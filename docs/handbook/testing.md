# Testing

## Why this exists

A test suite, a CI gate, or a config comment all carry the same risk: they read as evidence once written, whether or not they still tell the truth. A hook with no test of its own is a promise nobody has checked. A snapshot accepted without reading its diff is a rubber stamp wearing a green checkmark. A flaky test wrapped in a retry stops being a signal and starts being noise, and a coverage number chased as a target gets satisfied by tests that assert nothing. None of these failures announce themselves at the point they happen; the rules below are what this fleet, plus outside testing literature, has learned the hard way about catching them before they do.

Two of the rules arrived later than the rest, from a survey of the public Claude Code testing landscape captured 2026-08-24 (`docs/handbook/sources/testing-sweep.md`), paired with a general testing-doctrine catalog captured the same day (`docs/handbook/sources/testing-external.md`). That survey brought in a second kind of check entirely: an eval that measures whether a rule changes a model's behavior, which fails in ways a deterministic test cannot express. Those two rules now live in `docs/handbook/evals.md`, beside the measurement rules they extend; the vendor verdict and the deferred doctrine below stay here.

`pr-checks.yml` states the discipline this chapter closes on: name what the gate runs today, and say plainly what it deliberately does not gate, so a later reader can tell an accepted gap from an oversight rather than rediscovering it the hard way. Its own "Deliberately NOT gated here" block names the concrete example: migration and build validation are left out because a real CI fixture needs an anonymized export from the live database, which cannot be inferred from the codebase alone (TW-199). The tech-debt list keeps the same habit for tests specifically: it records which tests the backlog still owes and why each was deferred, because the missing test is usually the one whose fixture was too expensive to build on the day the rest of the sprint shipped (MEM-100).

## Give the agent a check it can run before you walk away

No incident recorded; the rule came in on reasoning alone, from Claude Code's own best-practices guidance: give the agent a check it can run before you walk away, tests, a build's exit code, a linter, a screenshot diff, because without a pass/fail signal "looks done" is the only signal there is, and without it you become the verification loop yourself (EXT-028). The `verify` skill name was added 2026-10-08 from the Claude Code 2.1.286 changelog (https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md, fetched 2026-10-08): when a project or user skill is named `verify`, Claude is told to run it right before committing, except for docs-only and tests-only commits.

Native floor, as of 2026-09-02: CLAUDE.md, loaded at the start of every session as context rather than enforcement, so naming the command there makes it findable and nothing more (https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory).

## Scale the pyramid to the repo you have, and route what the PR gate cannot afford

No incident recorded from inside the fleet; the rule is external, widely-held guidance, cited at two different grains. The base citation states the shape plainly: follow the pyramid, many fast unit tests, fewer integration tests, very few end-to-end tests, because filesystem and database integration is far slower and flakier per unit of coverage than a unit test is (EXT-040). The sweep's own elaboration routes that shape against what a repo can actually afford to run for free: keep the credential-free, second-scale tests in the pull-request gate, and route anything that needs a database, a network, or a secret to a scheduled run instead, so the gate stays runnable on a machine that holds no credential (EXT-077). The gate's own scope and wall-time target are a `github.md` concern and are not repeated here; this rule is the routing decision that produces that scope, not the scope itself.

## Test the guard itself, as its own CI step

repo-c's `scripts/test-no-direct-master.sh` is the source incident: a dedicated shell test for the hook that guards the workflow, wired as `npm run test:hook` and run as its own named CI step, justified directly in the workflow comment: "code that guards the workflow deserves a test more than most" (AS-032). Running it as a separate step, rather than folding it into the general suite, is deliberate: a guard failure then reads as a guard failure, not as one more red line inside an unrelated test run that someone might scroll past.

Native floor, as of 2026-09-02: hook debugging, which offers after-the-fact inspection only, the transcript view and a debug log, and proves nothing about whether a guard still fires (https://code.claude.com/docs/en/hooks-guide.md). The CLI's `claude plugin test` runs a mod's own tests "in an environment like the one the mod's hooks run in" (`claude plugin test --help`, Claude Code 2.1.306), which covers a mod's hooks module, not a command hook.

## Feed a real payload through the real wiring, and never re-implement the logic under test

repo-a's own `scripts/test-no-direct-master.sh` (`npm run test:hook`) is the incident: it replicates the hook's quote-strip and refspec-matching logic in isolation, requires both a true-positive case (must block) and a false-positive case (must allow), and deliberately constructs the literal tokens `git push` and `git commit` via `printf`, so the test file's own contents do not trip the installed hook it is exercising (TW-196). External guidance backs the same discipline from the mocking side, outside the fleet: never assert against a value the test computed the same way the code under test computes it, because that only proves two copies agree with each other, not that either one is right (EXT-078).

The sweep found two public repos that state the hook-specific form of this precisely, and both are worth copying at the mechanical level (EXT-097). `VoxCore84/claude-code-hook-tester` sends event-specific mock JSON on stdin for all 10 lifecycle events, overridable via `payloads.json`, and asserts exit codes with their real semantics: 0 passes, **2 is an intentional block**, and anything else is a crash. Getting that three-way contract right is the whole point, because a test that treats any non-zero as failure will call a working block a crash. `karanb192/claude-code-hooks` carries the same idea as a standing test category rather than a tool: an integration tier that drives the real stdin/stdout flow per plugin. Authoring the hook itself, and failing it closed, belong to `claude-code.md`; this chapter covers only how its test is fed.

Native floor, as of 2026-09-28: the documented hook contract, a per-event JSON payload on stdin, exit-code semantics where the blocking code is fixed per event, and stdout read as a decision only when it parses as JSON passing the hook output schema, an object failing that schema being a non-blocking error that lets the action through (https://code.claude.com/docs/en/hooks.md).

## Test behavior through the public interface, so a test changes only when a requirement changes

No incident recorded inside the fleet; this rule is external, from the test-maintenance research run of 2026-10-22 (`research/test-maintenance/2026-10-22.md`) and a corroboration pass that fetched independent sources. Software Engineering at Google, chapter 12, states the ideal: a test should never need to change unless the requirements of the system under test change, and a test that fails on an unrelated production change that introduces no real bug is brittle (EXT-119, https://abseil.io/resources/swe-book/html/ch12.html). Its fix is to test behavior through the public interface rather than implementation details, so that a pure refactor, a new feature, or a bug fix forces no edit to an existing test. Fowler's "Mocks Aren't Stubs" (https://martinfowler.com/articles/mocksArentStubs.html), fetched, agrees from outside Google: a classic test "only cares about the final state - not how that state was derived", and mockist tests are "more coupled to the implementation of a method". Confidence is medium: one practitioner book, corroborated by Fowler's article, which is a design essay and not a measurement. Google's own Testing on the Toilet posts on the same point come from the same organization, and only their comments were fetched, so they are not counted as independent. The book presents this as an ideal; real suites also change for readability refactors, fixture cleanup, and flakiness fixes.

Prefer the result a call produced over the calls made to reach it, and a real collaborator over a double when the real one is fast and deterministic (EXT-120, https://abseil.io/resources/swe-book/html/ch12.html). Two qualifications come from fetched sources and are in the rule. Classicists "use real objects if possible and a double if it's awkward to use the real thing", and Fowler's UnitTest note (https://martinfowler.com/bliki/UnitTest.html) says a classic tester still uses doubles for an awkward collaboration, which are "invaluable to remove non-determinism when talking to remote services". And some behavior has no observable state: "The whole point of a cache is that you can't tell from its state whether the cache hit or missed", so an interaction assertion is sometimes the only check. The book's claim that over-reliance on mocking frameworks is the most common cause of brittle interaction tests has no independent support, so it is attributed to the book alone and left out of the rule. Confidence is medium for the preference and low for that causal ranking. The mockist school (described in "Mocks Aren't Stubs") uses interaction tests as a design tool, pushing the shape of a collaboration into the open before the code exists; the rule takes the state side because a suite is read and edited for years after the design is settled.

This package's own example is the CLI test file, `tests/cli-house.test.mjs`, whose header has every test copy the real CLI into a throwaway plugin directory and run it as a subprocess against a throwaway repository, asserting on what it prints and exits with. Whether a test reaches past the interface is an editorial call, so nothing enforces the rule; the hook-payload form of the same obligation is the section above.

## Ship every gate with a positive control and a negative control

Operator memory states the rule as a standing discipline rather than a one-off fix: commit the case that must fail beside the case that must pass, so the suite itself carries the proof that a check can still fail, instead of trusting a clean run on faith (MEM-099, `feedback_no_op_is_not_evidence.md` and `project_css_diff_harness_traps.md`). Mutation-testing's own rationale states the same requirement from outside the fleet: give every gate a case it must fail as well as a case it must pass, because a suite of passing cases alone cannot tell a working check from one that always passes (EXT-079, widely-held, no single canonical source pinned by this sweep). The general form, proving a check can fail before trusting that it passed, lives in `engineering.md`; this rule is the narrower, suite-level obligation to carry both controls as committed cases, not a proof done once and then forgotten.

The sweep looked for this pattern upstream and did not find it: `plugin-validator` only reads files and never executes a plugin, `hookify` verifies in prose ("run this, you should see the warning") with no test at all, and `Emasoft/claude-plugins-validation` has 10,800-plus tests of the validator's own code but no documented corpus of deliberately-broken plugins proving the validator still detects them. A planted violation running in the same CI job as the passing case is one of the few places this module is ahead of what is published.

The eval tier needs the same two-sidedness, and here there is public agreement. `skill-bench/skill-eval-action` requires at least one negative trigger case (`expect_skill: false`) in every skill's eval set, and Anthropic's evals article states the reason in one line: "Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization" (EXT-096). An eval suite made only of should-fire cases optimizes a rule toward firing constantly, which is a different defect from the one it was written to catch.

## Read the snapshot diff before accepting it, because a snapshot is a drift gate

repo-a's `email-snapshots/` directory is the concrete example: the rendered artifact is committed, and CI re-renders it and runs `git diff --exit-code` against the committed copy, the same shape as the build-record's own HTML/Markdown twin check (TW-197). The rule is to actually read that diff before accepting a new snapshot, not merely let the gate turn green, because an unread diff turns a drift gate into a rubber stamp. Operator memory names four specific ways a diff harness lies to a reader who skips that step anyway: comparing baselines captured in different environments, a `git stash -- <paths>` that silently no-ops and leaves the "after" capture identical to the "before," a browser's own late-computed layout values reading as a false delta, and a snapshot keyed on a generated class name that changes every build (MEM-010, `project_css_diff_harness_traps.md`). Jest's own snapshot-testing guidance backs the same discipline from outside the fleet: keep a snapshot small enough that a person can actually hold its diff in mind, because a snapshot nobody can read gets accepted rather than reviewed (EXT-080).

## Quarantine a flaky test loudly, and never retry it into silence

repo-a's `results-feed.yml` is the concrete anchor: county-results fetching runs on a narrow, named-day cron plus manual dispatch, and is marked `continue-on-error` on purpose, so an outage on someone else's canvass feed never turns the whole workflow red, and the same live-upstream dependency recurs in the council-retrieval pipeline this row also cites (TW-198). The rule generalizes past that one workflow: pin a check that depends on a live upstream to a recorded fixture inside the gate itself, and run the live-hitting version on its own separate cadence, because a red that turns on someone else's uptime teaches the reader to ignore red. External guidance states the fuller discipline from outside the fleet: move a flaky test into a named quarantine list that the run itself reports, with an owner and a stated condition for taking it back out, because a silent retry converts an intermittent defect into silence and a deletion converts it into nothing (EXT-081, widely-held, no single canonical source pinned by this sweep). A corroboration pass on 2026-10-22 refines this in three ways, from fetched sources. A retry can be part of the discipline: Gradle's flaky-test practice (https://blog.gradle.org/how-we-handle-flaky-tests-in-gradle) is to "retry all failed tests, quarantine the too-flaky tests, and fix the flaky tests through teamwork", with flaky tests reviewed once per week, and Meta (https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/) treats a failure as "merely a hint to run the test again" and creates a ticket for the declared owner of the test. So the rule bans a retry nobody sees, not a retry that records a pass after a failure as a flake and routes it to the quarantine list and its owner (EXT-081, EXT-124). Fowler's non-determinism article (https://martinfowler.com/articles/nonDeterminism.html) says to quarantine a non-deterministic test but fix it quickly, warning that quarantined tests get forgotten, which is the case for a review cadence. And a claimed fix needs confirming before a test leaves quarantine: Lam and others (ICSE 2020, Microsoft, https://www.microsoft.com/en-us/research/publication/a-study-on-the-lifecycle-of-flaky-tests/) found developers' claimed fixes often did not fix or reduce flakiness, so the rule asks for a rerun enough times to show the flake is gone. Confidence is medium to high for quarantine with an owner and a review cadence. The recurrence claim is low: Google reported in 2016 that about 1.5 in 100 test runs gave a flaky result, almost 16 in 100 of its tests had some flakiness, about 84 in 100 of its pass-to-fail transitions involved a flaky test, and new flakiness arrived about as fast as old flakiness was fixed (EXT-124, https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html). No independent source confirmed those figures, the post publishes no method for the insertion and fix rates, they are a decade old and specific to Google, and its author says Google does not track how often flaky tests hide real bugs; read them as one organization's 2016 observation. Meta's data sits at a different scale: all real-world tests are flaky to some extent, unit tests well below 1 in 100 and some end-to-end frameworks up to about 10 in 100.

The full run adds the order of operations (EXT-129, medium confidence). Habchi and others (ICST 2022, https://orbilu.uni.lu/bitstream/10993/55847/1/ICST2022.pdf; 14 interviewees plus a review of 38 grey-literature articles) found fixing the root cause the most reported treatment (7 of 14 interviews, 15 of 38 articles). Reruns were common (7 of 14, 14 of 38), but one interviewee warned "you can ignore actual problems", and quarantine was less favored, one interviewee saying it transfers the bug to users. Only 2 of 14 had explicit anti-flakiness guidelines, and reliable infrastructure and monitoring and logging were each reported by 9 of 14. Atlassian's flaky-test tool (https://www.atlassian.com/blog/atlassian-engineering/taming-test-flakiness-how-we-built-a-scalable-tool-to-detect-and-manage-flaky-tests, a first-hand company blog with self-reported figures) reruns a failing test in the same build until the result flips, scores flakiness over recent runs, quarantines until a test stays healthy for a set period, and files a ticket with a due date for the owning team. The sources disagree on rerun-and-quarantine automation against practitioners who say it masks bugs; the common ground, and the rule, is to fix the cause first and treat quarantine as a holding state with an owning team and an exit deadline. Flakiness is also corrosive: teams learn to ignore failures, which lets real bugs through, and a test that fails every time is a better signal than a flaky one (medium). The sentence on skipped tests (a test skipped when a database, tool, or build is missing says so in the run output and names where it does run) comes from operator practice and is not a finding of the run.

Two handbook-only points, not in the rule. Most flakiness is perceived to come from outside the code under test: of the 14 interviewees, 11 cited the environment, 9 interactions of the system under test, 8 infrastructure, 8 poorly written tests, and only 3 the code under test (medium; these are perceptions, and one person could name several causes). The Google Testing Blog of 2017 (https://testing.googleblog.com/2017/04/) lists random numbers, timeouts, and absolute or relative timing between threads as causes and finds flakiness rises with test size even among mostly hermetic tests. Hermetic, ephemeral environments, a fresh system under test per test with owned dependencies in sandboxed containers, are reported to reduce integration-test flakiness (Arguelles, ICST 2023 workshop, https://conf.researchr.org/details/icst-2023/cciw-2023-papers/3/How-we-use-Hermetic-Ephemeral-Test-Environments-at-Google-to-reduce-Test-Flakiness), but confidence is low: it is a single workshop abstract with no before-and-after numbers, and it names costs, with complex systems taking ten to thirty minutes to start and slow data seeding.

## Delete a test with the code it covered, and prove a test redundant before removing it as a duplicate

No incident recorded inside the fleet; external. The only study of deletion the run found is "Understanding Test Deletion in Java Applications" (MSR 2025, abstract at https://2025.msrconf.org/details/msr-2025-technical-papers/24/Understanding-Test-Deletion-in-Java-Applications, full paper read at https://hifromajay.github.io/papers/msr25.pdf): 24,431 manually confirmed deleted tests across seven open-source Java projects. About 91 in 100 deleted tests were obsolete, meaning their production code had been deleted, but that holds for six of the seven projects; the excluded project held about 70 in 100 of all deletions. About 38 in 100 of the obsolete tests were deleted in a later commit and about 62 in 100 in the same commit as their code. About 7 in 100 deleted tests (518) were redundant passing tests, and 92 in 100 of those came from one project (pmd) (EXT-121). So the common, safe deletion is the test that goes with the code it covered, and the rule asks for it in the same change. Confidence is low to medium: one peer-reviewed study of open-source Java, describing what developers do, which is not proof that it is best practice.

The abstract's two warning figures are easy to misread, and the full paper corrects them (EXT-122). The "20%" is not an experiment that deleted a fifth of the tests: of the 518 tests developers deleted as redundant, 103 each lowered line or branch coverage when removed individually, and 66 of 369 lowered the mutation score, with a median loss of 5 in 100 line coverage, 7 in 100 branch coverage and 12 in 100 mutation score. So about one deletion in five that developers judged redundant lost coverage. The "54%" is the best case of one family of similarity-based reduction tools (FAST-R), under a loose budget and pooled across projects; a strict budget gave about 8 in 100 on one project, and no approach was consistent across projects. The authors say the approaches can be used as a filtering step. The rule follows that: a person removing a test as a duplicate names the test that still covers the behavior and shows it fail on the defect the removed one caught, with a planted fault or a mutation, and treats a reduction tool's output as a filter and not a verdict. That naming-and-showing step is a reasonable reading of the findings, not something the study tested. A positive and negative control pair is one unit: its negative half looks redundant beside the positive until the gate breaks (see the controls section above). Nothing checks a redundancy claim, so the planted-fault run shown in the change is the control. An older study of reduction losing fault detection on changes (Shi and others, FSE 2015) was seen only as a search snippet and is unverified here.

The full run adds a high-confidence reason not to shrink a suite by coverage (EXT-127), from three peer-reviewed sources. Shi, Gyori and others (ISSTA 2018, https://mir.cs.illinois.edu/gyori/pubs/issta18.pdf) replayed 1,478 failed builds across 32 GitHub projects: reduction cut suite size by 51.9% to 61.1% while coverage or mutant loss was only 2.2% to 2.7%, yet the share of failed builds the reduced suite could still detect fell by up to 52.2%. Traditional metrics were poor predictors of that loss, and even their best historical predictor was still not a good one. An oracle that kept only the tests that fail in future would be about 20% of the suite, so the potential saving is real; the coverage-based way of finding it is what fails. Noemmer and Haas (SWQD 2020, https://teamscale.com/hubfs/26978363/Publications/2020-test-suite-minimization-swqd.pdf?hsLang=en, seven projects) found greedy and HGS statement-coverage minimization cut suite size and time by over 70% but lost about 12.5% of the mutation score (3.5% to 21% by project); simple greedy did about as well as HGS, and dropping the coverage requirement removed 86.7% of tests against 69.2% at a much larger loss. Test-count reduction poorly predicted time saved (4.5% to 68.6%), because a few long tests dominate runtime, which is why the rule says to move or remove a few long-running tests rather than many cheap ones when the goal is speed. Older literature disagrees: Rothermel and others found significant losses, while Zhang and Wong and others found small or negligible ones; the post-2015 evidence sides with caution, and the authors say minimization is rarely used in practice. Limits: mostly open-source Java, and the first study measures failed-build detection, not escaped bugs. The MSR 2025 reading above also supports it: developers delete tests in small steps, usually with their production code, and even tests judged redundant can carry detection value (medium).

## Fix the test smells that hide what broke, not the ones a detector counts

No incident recorded inside the fleet; external, with evidence that pulls in more than one direction, so confidence is medium to low. In an interview study of six small open-source Java projects (Campos and others, a 2021 preprint with no venue found, arXiv 2107.13902, https://arxiv.org/pdf/2107.13902), developers rated 42 of 48 detected smells, about 87 in 100, as low severity, and rated Assertion Roulette (many assertions with no message saying which failed) the most harmful and most variable, followed by Eager Test (one test checking several behaviors) and Unknown Test (no assertion). The MSR 2020 paper on severity thresholds (https://2020.msrconf.org/details/msr-2020-papers/14/Investigating-Severity-Thresholds-for-Test-Smells) calls ranking detected smells by severity an open research topic (EXT-123).

Three fetched sources qualify that picture. First, "most smells are low severity" is developer perception, not measured harm: Bavota and others (EMSE 2015, https://www.iris.unisa.it/handle/11386/4465858) found test smells have a strong negative impact on program comprehension and maintenance, with comprehension about 30 in 100 better without them. Second, Tufano and others (ASE 2016, https://microsoft.com/en-us/research/?p=771931) found developers often fail to recognize harmful smells, so perception ratings may undercount harm. Third, "Test smells 20 years later" (Panichella and others, EMSE 2022, https://research.tudelft.nl/en/publications/test-smells-20-years-later-detectability-validity-and-reliability) found the current vocabulary of test smells highly mismatched to real concerns, and an older tool's detection strategies misclassified over 70 in 100 of test smells. That last finding is why the rule calls a detector's output unreliable triage input, neither a backlog nor a severity ranking. A snippet-only report that Indirect Testing, Eager Test and Assertion Roulette are the strongest predictors of change-proneness (Spadini and others, ICSME 2018) is unverified and not relied on. Nothing found supports a test with no assertion as a priority, so the rule drops it and names the eager test and assertion roulette. The rule does not imply the other smells are harmless.

The same Tufano study is the high-confidence part of this section and the basis for reviewing a test's smells in the change that adds it (EXT-126, https://microsoft.com/en-us/research/?p=771931). Across 152 projects it found smells are usually introduced when the test code is first committed and tend to remain for a long time; a verifier noted that about 80% were still unfixed after 1,000 days, a figure from the verifier's reading and not a quoted result. In its 19-person perception study developers generally did not recognize harmful smells. Several peer-reviewed sources agree, so confidence is high for the timing and persistence, and the rule asks for review at introduction because later cleanup is unlikely to happen. Two lower-confidence points sit beside it. Refactoring test smells by hand is error-prone and tooling is limited, so review a test refactoring and rerun detection afterwards (low; the 2016 statement that no automated tools exist is outdated, since detectors such as tsDetect and JNose now exist). And complex production classes, by cyclomatic complexity and weighted methods per class, go with Eager Test and duplicated-code smells in their unit tests (low; one study), a cheap pointer to where test refactoring is likely needed.

## Treat coverage as a search-light, never as a target

No incident recorded inside the fleet; this rule is external, from the same widely-held coverage guidance cited twice. Use coverage to find code that nothing exercises, and never set it as a target, because a number chased as a goal gets met by tests written for the number rather than for the behavior (EXT-082). Read the uncovered branches themselves rather than the summary percentage, and take a coverage threshold back out of the gate the moment it starts producing tests with no real assertion inside them (EXT-083). Whether a solo repo should gate on a coverage number at all is contested even in the wider guidance; the one point every source agrees on is that a threshold, once set as a goal, stops measuring what it was named for (EXT-085, the sweep's own disagreement note). The 2026-10-22 run and a corroboration pass add a way to read coverage that survives that disagreement: on the change under review, asking what the diff adds that nothing runs. Fowler's coverage note (https://martinfowler.com/bliki/TestCoverage.html, fetched) says that if you make a certain level of coverage a target, people will try to attain it, and calls coverage a useful tool for finding untested parts of a codebase, which is the basis for the rule's reason that a number set as a goal gets gamed. Google's coverage paper (ESEC/FSE 2019, https://research.google/pubs/code-coverage-at-google/) says applying coverage at the level of changesets and code review is what makes it actionable; that is Google's own practice and not independent, so confidence is medium. An industrial case study of 11,424 unit tests (https://arxiv.org/pdf/2103.08480) found 291 of 2,041 methods, about 14 in 100, pseudo-tested, meaning their bodies could be removed with no test failing, though 835 of their 1,129 lines counted as covered; counting those lines as uncovered would lower line coverage from 89 to 82 in 100 (EXT-125). A covered line is therefore not a tested line, and a path that matters is worth checking with a planted fault or a mutation; that conclusion is medium to high confidence, but the data is one industrial project whose language was not confirmed. The practiced pairing is mutation testing on changed code only: Google's "Practical Mutation Testing at Scale" (Petrovic and others, https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/, fetched) mutates only the changed code during code review, rather than the entire code base. A Google Testing Blog post calling coverage a reasonable, objective, industry-standard metric with actionable data was seen only as a snippet and is unverified; if it is accurate, "never a target" is stronger than Google's own wording, which is why the rule rests on gaming and not on rejecting coverage numbers outright.

The full run found no verified source that ties a coverage level to defect rates (open question below). The only remarks are anonymous comments on a 2014 Google Testing Blog post saying no correlation had been found yet, which are anecdote and not a finding. The ISSTA 2018 result under the deletion section (low coverage loss alongside high real detection loss) also says coverage is a weak proxy for whether a test is redundant. Read these as the reason the rule says what coverage is for, finding what nothing exercises, and does not say what a level of it predicts (medium).

## Mirror the module layout in the test tree, and keep each fixture beside its test

repo-a's `vitest.config.mjs` states the layout directly: `include: ['tests/**/*.test.{mjs,js,ts}']`, every test living flat in a single `/tests` directory (56 files at last count), fixtures held in `tests/fixtures/`, and each file named `<subject>.test.{mjs,ts}` to mirror the `scripts/lib/*` or `src/lib/*` module it exercises (TW-134). A reader who cannot find the test for a file assumes there is none and writes a second one; the flat, mirrored layout is what keeps that assumption from being wrong.

Two additions came with the 2026-10-22 run. First, the module's default load paths are `**/tests/**`, `**/test/**`, `**/*.test.*`, and `**/*.spec.*`. Claude Code matches a rule's `paths:` globs relative to the directory that holds `.claude/` ("Each pattern is relative to the rule's base directory", https://code.claude.com/docs/en/memory, "Path-specific rules"), so the earlier default of top-level `tests/**` and `test/**` never loaded the testing rules for tests kept in a nested package directory or beside the source. One adopter surveyed had about 35 test files under a nested `tests/` directory that never loaded them. A repo that sets `testRoots` explicitly keeps its own value, and `tests/a.test.mjs` still matches (`tests/testing-default-paths.test.mjs`). Second, share setup only where the shared values do not hide what a test depends on (EXT-128, medium confidence). Software Engineering at Google, chapter 12 (https://abseil.io/resources/swe-book/html/ch12.html), prefers readability over deduplication, DAMP over DRY: a little duplication is acceptable if it lets each test read as a complete story, and shared setup and helpers make tests unclear when a test depends on the particular values used in the setup. It says DAMP is not a replacement for DRY but complementary to it, and defines a clear test as one whose purpose and reason for failing are immediately clear to the engineer diagnosing a failure. Only this one book was verified. Fowler, Beck, and Meszaros's xUnit Test Patterns keep DRY helpers for setup, and the tension is how far to deduplicate, so the rule stops where shared values hide what a test depends on; that wider disagreement was recalled by verifiers and not fetched.

## Explain a test-runner config quirk in the config, with the incident that produced it

The same `vitest.config.mjs` carries a 15-line comment on its `oxc: { jsx: ... }` setting, explaining why the older `esbuild.jsx` spelling is silently ignored and why fixing the setting centrally beats a scoped `tsconfig` per template directory, with the incident stated inline: "that is not hypothetical: it broke the three email suites on the Astro 7 upgrade" (TW-135). The comment is falsifiable rather than decorative precisely because it names the concrete thing that breaks without it, instead of describing the setting in the abstract.

## Keep a demoted check running, reported, and counted

No incident recorded inside the fleet; the rule is external, widely-held guidance drawn from the general alert-fatigue literature around continuous integration: demote a suite check that has produced a false positive to advisory rather than deleting it, and print its false-positive tally in the run output, because a red that is usually wrong trains the reader to skip every red, the true ones included (EXT-084, widely-held, no single canonical source pinned by this sweep). Deciding when a check has earned demotion, and how a checker carries its own tally, are `engineering.md`-level calls; this rule is narrower, the suite-level obligation to keep a demoted check running, reported, and counted rather than quietly dropped.

## Rejected alternatives

**Adopt no eval vendor** (PA-038). The sweep evaluated four and recommended none. `promptfoo` (24.5k stars, OSS) is the closest competitor and the only vendor with a first-class `skill-used` / `not-skill-used` assertion normalized from Skill tool calls, plus fixture directories to A/B two SKILL.md versions, but it duplicates `--ablation with-without` and adds a YAML dialect to learn. `DeepEval` offers 50-plus metrics built for RAG and model regression, which is the wrong shape for behavioral rules. `Braintrust` and `LangSmith` are hosted and account-gated, with dashboards nobody here would open, though LangSmith's published 82%/9% finding is worth citing. `MLflow`'s `autolog claude` loop, which feeds failing judge rationales back to Claude to auto-patch a SKILL.md, is the most interesting of the four and the heaviest dependency. The built-in already provides cases, six grader types, ablation, repeats, and cost ceilings with no new dependency and no API-key plumbing; revisit only for cross-model sweeps it cannot express.

**Golden transcript snapshots of an agent run** (EXT-095). Snapshotting a whole agent trajectory and diffing it looks like the snapshot rule above applied to evals, and it is not: Anthropic warns explicitly that path matching is "too rigid... agents regularly find valid approaches that eval designers didn't anticipate." No credible upstream does this. Grade the artifact and the end state instead.

**Doctrine read and deliberately not ported at this pass** (EXT-098). The second catalog, `docs/handbook/sources/testing-external.md`, carries five bodies of guidance this module does not yet state as rules: test-first ordering with the red-green discipline (watch the test fail for the intended reason; treat a first-run pass as a red flag), property-based and mutation testing (round-trips and invariants; mutation runs narrow and nightly, surviving mutants read as a worklist), condition-based waiting instead of sleeps, factories with minimal valid defaults over large static fixtures, and test-naming conventions. Each is a full heading's worth of rule, the module's heading budget was spent on the eval split, and the catalog also records nine points where its own sources disagree (strict TDD versus tests-after, mocking, retries, the pyramid's shape, coverage thresholds, fixtures versus factories). Recorded here so the deferral is visible rather than silent.
