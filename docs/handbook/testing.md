# Testing

## Why this exists

A test suite, a CI gate, or a config comment all carry the same risk: they read as evidence once written, whether or not they still tell the truth. A hook with no test of its own is a promise nobody has checked. A snapshot accepted without reading its diff is a rubber stamp wearing a green checkmark. A flaky test wrapped in a retry stops being a signal and starts being noise, and a coverage number chased as a target gets satisfied by tests that assert nothing. None of these failures announce themselves at the point they happen; the rules below are what this fleet, plus outside testing literature, has learned the hard way about catching them before they do.

Two of the rules arrived later than the rest, from a survey of the public Claude Code testing landscape captured 2026-08-24 (`docs/handbook/sources/testing-sweep.md`), paired with a general testing-doctrine catalog captured the same day (`docs/handbook/sources/testing-external.md`). That survey is the reason this chapter now covers a second kind of check entirely: an eval that measures whether a rule changes a model's behavior, which fails in ways a deterministic test cannot express.

`pr-checks.yml` states the discipline this chapter closes on: name what the gate runs today, and say plainly what it deliberately does not gate, so a later reader can tell an accepted gap from an oversight rather than rediscovering it the hard way. Its own "Deliberately NOT gated here" block names the concrete example: migration and build validation are left out because a real CI fixture needs an anonymized export from the live database, which cannot be inferred from the codebase alone (TW-199). The tech-debt list keeps the same habit for tests specifically: it records which tests the backlog still owes and why each was deferred, because the missing test is usually the one whose fixture was too expensive to build on the day the rest of the sprint shipped (MEM-100).

## Give the agent a check it can run before you walk away

No incident recorded; the rule came in on reasoning alone, from Claude Code's own best-practices guidance: give the agent a check it can run before you walk away, tests, a build's exit code, a linter, a screenshot diff, because without a pass/fail signal "looks done" is the only signal there is, and without it you become the verification loop yourself (EXT-028).

## Scale the pyramid to the repo you have, and route what the PR gate cannot afford

No incident recorded from inside the fleet; the rule is external, widely-held guidance, cited at two different grains. The base citation states the shape plainly: follow the pyramid, many fast unit tests, fewer integration tests, very few end-to-end tests, because filesystem and database integration is far slower and flakier per unit of coverage than a unit test is (EXT-040). The sweep's own elaboration routes that shape against what a repo can actually afford to run for free: keep the credential-free, second-scale tests in the pull-request gate, and route anything that needs a database, a network, or a secret to a scheduled run instead, so the gate stays runnable on a machine that holds no credential (EXT-077). The gate's own scope and wall-time target are a `github.md` concern and are not repeated here; this rule is the routing decision that produces that scope, not the scope itself.

## Split deterministic tests from model-behavior evals, and give each its own budget and cadence

`obra/superpowers` (MIT, 277k stars, pushed 2026-08-19) is the clearest public example of the split, and the sweep ranked it the single highest-value pattern available to borrow (EXT-086). That repo keeps two directories with two different contracts. `tests/` holds bash, node, and python infrastructure tests run by `run-*.sh` and `npm test`, and is CI-safe. `evals/` holds the **drill** harness, which drives real tmux sessions of Claude Code, Codex, and Gemini CLI with an LLM actor and an LLM verifier, from scenarios in `evals/scenarios/*.yaml`, at 3 to 30-plus minutes and real API cost per scenario. The eval directory is explicitly excluded from CI (EXT-088). That exclusion is the load-bearing half: a tier that costs money and answers differently on each run cannot be the thing that decides whether a merge may land, because the first time it is red for an unreproducible reason it gets switched off, and nothing else in the repo notices it is gone.

`karanb192/claude-code-hooks` (MIT, 485 stars, pushed 2026-08-23) shows the deterministic tier done well and cheaply: Node's built-in runner (`node --test`), zero npm dependencies, tests colocated at `plugins/<name>/tests/<name>.test.js` across 20 plugins, and three explicit categories (unit tests of core functions, integration tests of the stdin/stdout flow, config validation). Its CI runs a Node 18/20/22 matrix with `fail-fast: false`. We adopt the runner shape and the colocation, and scope the matrix out: this package pins Node 22.12+, so a version matrix buys little here (PA-037).

Budgets are what make the second tier survivable. The built-in `claude plugin eval` takes `--max-cost-usd` and exits 2 on overage; `TribeAI/claude-evals` caps a task at $0.50 (EXT-087). Write that ceiling as an invariant rather than a habit, which is `engineering.md`'s rule, and read account-wide Actions minutes as `github.md`'s, since the two budgets are separately exhaustible.

Two eval-harness practices are worth borrowing without becoming rules. The headless probe: run `claude -p "$PROMPT" --plugin-dir … --dangerously-skip-permissions --max-turns N --output-format stream-json`, then grep the JSON trace for the `Skill` tool call plus a skill-name regex, and separately detect "premature action", a non-Skill tool firing before the Skill (superpowers `tests/explicit-skill-requests/run-test.sh`; PA-035). And per-case isolation: `claude plugin eval` scaffolds each case into a throwaway workspace with a fresh `HOME` and `CLAUDE_CONFIG_DIR`, loads only the plugin under test, and deletes credentials at the end, which matches the "each trial starts from a clean environment" line in Anthropic's evals article (PA-039). One caveat worth writing down: that isolation does not block the network, so it is not an OS sandbox and should not be described as one.

## Test the guard itself, as its own CI step

repo-c's `scripts/test-no-direct-master.sh` is the source incident: a dedicated shell test for the hook that guards the workflow, wired as `npm run test:hook` and run as its own named CI step, justified directly in the workflow comment: "code that guards the workflow deserves a test more than most" (AS-032). Running it as a separate step, rather than folding it into the general suite, is deliberate: a guard failure then reads as a guard failure, not as one more red line inside an unrelated test run that someone might scroll past.

## Feed a real payload through the real wiring, and never re-implement the logic under test

repo-a's own `scripts/test-no-direct-master.sh` (`npm run test:hook`) is the incident: it replicates the hook's quote-strip and refspec-matching logic in isolation, requires both a true-positive case (must block) and a false-positive case (must allow), and deliberately constructs the literal tokens `git push` and `git commit` via `printf`, so the test file's own contents do not trip the installed hook it is exercising (TW-196). External guidance backs the same discipline from the mocking side, outside the fleet: never assert against a value the test computed the same way the code under test computes it, because that only proves two copies agree with each other, not that either one is right (EXT-078).

The sweep found two public repos that state the hook-specific form of this precisely, and both are worth copying at the mechanical level (EXT-097). `VoxCore84/claude-code-hook-tester` sends event-specific mock JSON on stdin for all 10 lifecycle events, overridable via `payloads.json`, and asserts exit codes with their real semantics: 0 passes, **2 is an intentional block**, and anything else is a crash. Getting that three-way contract right is the whole point, because a test that treats any non-zero as failure will call a working block a crash. `karanb192/claude-code-hooks` carries the same idea as a standing test category rather than a tool: an integration tier that drives the real stdin/stdout flow per plugin. Authoring the hook itself, and failing it closed, belong to `claude-code.md`; this chapter covers only how its test is fed.

## Ship every gate with a positive control and a negative control

Operator memory states the rule as a standing discipline rather than a one-off fix: commit the case that must fail beside the case that must pass, so the suite itself carries the proof that a check can still fail, instead of trusting a clean run on faith (MEM-099, `feedback_no_op_is_not_evidence.md` and `project_css_diff_harness_traps.md`). Mutation-testing's own rationale states the same requirement from outside the fleet: give every gate a case it must fail as well as a case it must pass, because a suite of passing cases alone cannot tell a working check from one that always passes (EXT-079, widely-held, no single canonical source pinned by this sweep). The general form, proving a check can fail before trusting that it passed, lives in `engineering.md`; this rule is the narrower, suite-level obligation to carry both controls as committed cases, not a proof done once and then forgotten.

The sweep looked for this pattern upstream and did not find it: `plugin-validator` only reads files and never executes a plugin, `hookify` verifies in prose ("run this, you should see the warning") with no test at all, and `Emasoft/claude-plugins-validation` has 10,800-plus tests of the validator's own code but no documented corpus of deliberately-broken plugins proving the validator still detects them. A planted violation running in the same CI job as the passing case is one of the few places this module is ahead of what is published.

The eval tier needs the same two-sidedness, and here there is public agreement. `skill-bench/skill-eval-action` requires at least one negative trigger case (`expect_skill: false`) in every skill's eval set, and Anthropic's evals article states the reason in one line: "Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization" (EXT-096). An eval suite made only of should-fire cases optimizes a rule toward firing constantly, which is a different defect from the one it was written to catch.

## Prove an eval can fail, then grade it with the cheapest grader that can

An eval that cannot fail is decoration, and the cheapest way to find out is the ablation. `claude plugin eval --ablation with-without` runs the same cases twice, once with the plugin loaded and once without, and reports a per-grader delta between the arms; the delta, not the pass rate, is the measurement (EXT-089). Anthropic's skill best-practices page builds the same step into its five-step loop: run the task without the skill first to find the real gaps, then establish a baseline before writing instructions. LangSmith's published finding shows what a large delta looks like in practice (82% task completion with skills against 9% without, with invocation still only around 70% even when the skill is explicitly prompted); the sweep's verdict was to steal the finding, not the platform. A rule that scores identically in both arms has taught the model nothing, and a suite full of those reports a number that never moves no matter what you write.

Write the cases before the prose. Anthropic's page says it outright: "Create evaluations BEFORE writing extensive documentation," with a checklist requiring at least three evaluations and a pass tested against Haiku, Sonnet, and Opus. The canonical rule for that ordering already lives in `claude-code.md` as part of making a procedure a skill (EXT-038), so this file points rather than restates. Note one staleness in that page as of the sweep: it says "There is not currently a built-in way to run these evaluations," which `claude plugin eval` has since falsified.

The grader ladder comes from the built-in runner's own guidance: "Prefer deterministic graders for long artifacts; llm judges are noisy on long inputs" (EXT-090). It ships six grader types, `regex`, `tool_used` (with `input_match`, `min`, `max`), `tool_order`, `file_exists` (a glob over created paths), `llm`, and `baseline`, and skill invocation is checked with `tool_used: Skill` plus an `input_match` regex rather than with a judge. Anthropic's evals article names the same three classes, code, model, and human, in the same order of preference. `llm-output.md`'s deterministic-backbone rule is this one level up: a fixed code path wherever the steps are knowable, the model only for what you cannot enumerate.

Repeats are not optional for a nondeterministic instrument. `claude plugin eval` defaults to `runs: 3` per case with `--threshold` defaulting to 1.0; skill-creator's `aggregate_benchmark.py` reports mean, stddev, min, and max of pass rate, latency, and tokens; superpowers' own guidance asks for 5-plus repetitions before believing a scenario result (EXT-091). Anthropic's article adds the distinction worth reporting alongside the spread: pass@k (succeeded at least once in k tries) and pass^k (succeeded every time) answer different questions, and quoting one while meaning the other is the eval-tier version of `engineering.md`'s rule that one number is never the accuracy.

Then grade the grader. skill-creator's `grader.md` agent does double duty: it grades the run and critiques the eval, flagging assertions that are "too easy to satisfy," and its `run_loop.py` supports a train/test split so a rule is not tuned against the same cases that certify it (EXT-092, PA-036). Anthropic states the human half: "You won't know if your graders are working well unless you read the transcripts," alongside a task-quality bar worth borrowing, that two domain experts should independently reach the same pass/fail verdict on a good task. Two related practices sit at the same layer: pin a cheap model as a canary to find the rule that only works because a large model is smart (superpowers' `run-haiku-test.sh`, and Anthropic's Haiku/Sonnet/Opus checklist), and blind the comparison, unblinding only for analysis, which this fleet already does through `llm-output.md` and its harder-won corollary that blind panels leak through derived fields (PA-039). One point where this module is stricter than anything published: skill-creator has a train/test split, but nobody upstream says what happens after you look at the test set, and `engineering.md`'s answer, that a holdout is spent the moment you measure against it and that fact gets recorded, is the rule that keeps an eval suite from quietly becoming a training set.

A final grading preference from the same article, worth stating even though it did not earn its own rule: "It's often better to grade what the agent produced, not the path it took" (EXT-094). The `file_exists` grader globbing over created paths is that preference expressed as a grader type, and this fleet already grades end state in `scripts/lib/retro.mjs` invariants.

## Read the snapshot diff before accepting it, because a snapshot is a drift gate

repo-a's `email-snapshots/` directory is the concrete example: the rendered artifact is committed, and CI re-renders it and runs `git diff --exit-code` against the committed copy, the same shape as the build-record's own HTML/Markdown twin check (TW-197). The rule is to actually read that diff before accepting a new snapshot, not merely let the gate turn green, because an unread diff turns a drift gate into a rubber stamp. Operator memory names four specific ways a diff harness lies to a reader who skips that step anyway: comparing baselines captured in different environments, a `git stash -- <paths>` that silently no-ops and leaves the "after" capture identical to the "before," a browser's own late-computed layout values reading as a false delta, and a snapshot keyed on a generated class name that changes every build (MEM-010, `project_css_diff_harness_traps.md`). Jest's own snapshot-testing guidance backs the same discipline from outside the fleet: keep a snapshot small enough that a person can actually hold its diff in mind, because a snapshot nobody can read gets accepted rather than reviewed (EXT-080).

## Quarantine a flaky test loudly, and never retry it into silence

repo-a's `results-feed.yml` is the concrete anchor: county-results fetching runs on a narrow, named-day cron plus manual dispatch, and is marked `continue-on-error` on purpose, so an outage on someone else's canvass feed never turns the whole workflow red, and the same live-upstream dependency recurs in the council-retrieval pipeline this row also cites (TW-198). The rule generalizes past that one workflow: pin a check that depends on a live upstream to a recorded fixture inside the gate itself, and run the live-hitting version on its own separate cadence, because a red that turns on someone else's uptime teaches the reader to ignore red. External guidance states the fuller discipline from outside the fleet: move a flaky test into a named quarantine list that the run itself reports, with an owner and a stated condition for taking it back out, because a silent retry converts an intermittent defect into silence and a deletion converts it into nothing (EXT-081, widely-held, no single canonical source pinned by this sweep).

## Treat coverage as a search-light, never as a target

No incident recorded inside the fleet; this rule is external, from the same widely-held coverage guidance cited twice. Use coverage to find code that nothing exercises, and never set it as a target, because a number chased as a goal gets met by tests written for the number rather than for the behavior (EXT-082). Read the uncovered branches themselves rather than the summary percentage, and take a coverage threshold back out of the gate the moment it starts producing tests with no real assertion inside them (EXT-083). Whether a solo repo should gate on a coverage number at all is contested even in the wider guidance; the one point every source agrees on is that a threshold, once set as a goal, stops measuring what it was named for (EXT-085, the sweep's own disagreement note).

## Mirror the module layout in the test tree, and keep each fixture beside its test

repo-a's `vitest.config.mjs` states the layout directly: `include: ['tests/**/*.test.{mjs,js,ts}']`, every test living flat in a single `/tests` directory (56 files at last count), fixtures held in `tests/fixtures/`, and each file named `<subject>.test.{mjs,ts}` to mirror the `scripts/lib/*` or `src/lib/*` module it exercises (TW-134). A reader who cannot find the test for a file assumes there is none and writes a second one; the flat, mirrored layout is what keeps that assumption from being wrong.

## Explain a test-runner config quirk in the config, with the incident that produced it

The same `vitest.config.mjs` carries a 15-line comment on its `oxc: { jsx: ... }` setting, explaining why the older `esbuild.jsx` spelling is silently ignored and why fixing the setting centrally beats a scoped `tsconfig` per template directory, with the incident stated inline: "that is not hypothetical: it broke the three email suites on the Astro 7 upgrade" (TW-135). The comment is falsifiable rather than decorative precisely because it names the concrete thing that breaks without it, instead of describing the setting in the abstract.

## Keep a demoted check running, reported, and counted

No incident recorded inside the fleet; the rule is external, widely-held guidance drawn from the general alert-fatigue literature around continuous integration: demote a suite check that has produced a false positive to advisory rather than deleting it, and print its false-positive tally in the run output, because a red that is usually wrong trains the reader to skip every red, the true ones included (EXT-084, widely-held, no single canonical source pinned by this sweep). Deciding when a check has earned demotion, and how a checker carries its own tally, are `engineering.md`-level calls; this rule is narrower, the suite-level obligation to keep a demoted check running, reported, and counted rather than quietly dropped.

## Rejected alternatives

**Adopt no eval vendor** (PA-038). The sweep evaluated four and recommended none. `promptfoo` (24.5k stars, OSS) is the closest competitor and the only vendor with a first-class `skill-used` / `not-skill-used` assertion normalized from Skill tool calls, plus fixture directories to A/B two SKILL.md versions, but it duplicates `--ablation with-without` and adds a YAML dialect to learn. `DeepEval` offers 50-plus metrics built for RAG and model regression, which is the wrong shape for behavioral rules. `Braintrust` and `LangSmith` are hosted and account-gated, with dashboards nobody here would open, though LangSmith's published 82%/9% finding is worth citing. `MLflow`'s `autolog claude` loop, which feeds failing judge rationales back to Claude to auto-patch a SKILL.md, is the most interesting of the four and the heaviest dependency. The built-in already provides cases, six grader types, ablation, repeats, and cost ceilings with no new dependency and no API-key plumbing; revisit only for cross-model sweeps it cannot express.

**Golden transcript snapshots of an agent run** (EXT-095). Snapshotting a whole agent trajectory and diffing it looks like the snapshot rule above applied to evals, and it is not: Anthropic warns explicitly that path matching is "too rigid... agents regularly find valid approaches that eval designers didn't anticipate." No credible upstream does this. Grade the artifact and the end state instead.

**Doctrine read and deliberately not ported at this pass** (EXT-098). The second catalog, `docs/handbook/sources/testing-external.md`, carries five bodies of guidance this module does not yet state as rules: test-first ordering with the red-green discipline (watch the test fail for the intended reason; treat a first-run pass as a red flag), property-based and mutation testing (round-trips and invariants; mutation runs narrow and nightly, surviving mutants read as a worklist), condition-based waiting instead of sleeps, factories with minimal valid defaults over large static fixtures, and test-naming conventions. Each is a full heading's worth of rule, the module's heading budget was spent on the eval split, and the catalog also records nine points where its own sources disagree (strict TDD versus tests-after, mocking, retries, the pyramid's shape, coverage thresholds, fixtures versus factories). Recorded here so the deferral is visible rather than silent.
