# Evals

## Why this exists

A measurement fails quietly in a way ordinary code does not: it still prints a number. A gate grading against a key its own tool wrote reports high accuracy that is only agreement with itself. A check that could not run prints the same zero as a clean one. A rate without its sample reads as certain from three runs. A baseline nobody can reproduce turns the next clean run into a phantom regression. And an eval that drives an agent can score a path no everyday session takes, or read the answer key through a search nobody denied. This chapter is the incident history behind each rule in `plugins/house/modules/evals/rules/evals.md`, drawn from repo-a's match-measurement work, the testing sweep of 2026-08-24, and a consuming repo's first agent-driven eval (issue #111).

These rules first sat in two other modules: the measurement rules in engineering, which loads on `scripts/**`, `src/**`, and `lib/**`, and the eval-tier rules in testing, which loads on `tests/**` and `test/**`. An eval harness most often lives in `evals/` or `eval/`, which neither path list reached, so the session editing an eval saw none of them (issue #119). They moved here unchanged under a path scope that loads where the harness lives; engineering and testing keep a one-sentence pointer each.

## Split deterministic tests from model-behavior evals, and give each its own budget and cadence

`obra/superpowers` (MIT, 277k stars, pushed 2026-08-19) is the clearest public example of the split, and the sweep ranked it the single highest-value pattern available to borrow (EXT-086). That repo keeps two directories with two different contracts. `tests/` holds bash, node, and python infrastructure tests run by `run-*.sh` and `npm test`, and is CI-safe. `evals/` holds the **drill** harness, which drives real tmux sessions of Claude Code, Codex, and Gemini CLI with an LLM actor and an LLM verifier, from scenarios in `evals/scenarios/*.yaml`, at 3 to 30-plus minutes and real API cost per scenario. The eval directory is explicitly excluded from CI (EXT-088). That exclusion is the load-bearing half: a tier that costs money and answers differently on each run cannot be the thing that decides whether a merge may land, because the first time it is red for an unreproducible reason it gets switched off, and nothing else in the repo notices it is gone.

`karanb192/claude-code-hooks` (MIT, 485 stars, pushed 2026-08-23) shows the deterministic tier done well and cheaply: Node's built-in runner (`node --test`), zero npm dependencies, tests colocated at `plugins/<name>/tests/<name>.test.js` across 20 plugins, and three explicit categories (unit tests of core functions, integration tests of the stdin/stdout flow, config validation). Its CI runs a Node 18/20/22 matrix with `fail-fast: false`. We adopt the runner shape and the colocation, and scope the matrix out: this package pins Node 22.12+, so a version matrix buys little here (PA-037).

Budgets are what make the second tier survivable. The built-in `claude plugin eval` takes `--max-cost-usd` and exits 2 on overage, and from Claude Code 2.1.283 it needs git 2.31 or later (https://code.claude.com/docs/en/plugin-evals); `TribeAI/claude-evals` caps a task at $0.50 (EXT-087). Write that ceiling as an invariant rather than a habit, which is `engineering.md`'s rule, and read account-wide Actions minutes as `github.md`'s, since the two budgets are separately exhaustible.

Two eval-harness practices are worth borrowing without becoming rules. The headless probe: run `claude -p "$PROMPT" --plugin-dir … --dangerously-skip-permissions --max-turns N --output-format stream-json`, then grep the JSON trace for the `Skill` tool call plus a skill-name regex, and separately detect "premature action", a non-Skill tool firing before the Skill (superpowers `tests/explicit-skill-requests/run-test.sh`; PA-035). And per-case isolation: `claude plugin eval` scaffolds each case into a throwaway workspace with a fresh `HOME` and `CLAUDE_CONFIG_DIR`, loads only the plugin under test, and deletes credentials at the end, which matches the "each trial starts from a clean environment" line in Anthropic's evals article (PA-039). One caveat worth writing down: a case's allowed_tools cannot grant Bash or Write, so a case that needs either runs only when the command grants it with the allow-tools flag, and a Bash grant then runs under the harness's OS-level sandbox, which confines writes to the run's workspace and limits network access to granted domains.

Native floor, as of 2026-09-28: the plugin eval runner's `--max-cost-usd` ceiling, checked before each run starts, which starts nothing further once spent, lets in-flight runs finish, and exits 2 with partial results, and its per-case threshold, which exits non-zero on a shortfall (https://code.claude.com/docs/en/plugin-evals; also `claude plugin eval --help`), and the budget-and-threshold practice they complement is written up in the skill-creator article (https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills).

## Prove an eval can fail, then grade it with the cheapest grader that can

An eval that cannot fail is decoration, and the cheapest way to find out is the ablation. `claude plugin eval --ablation with-without` runs the same cases twice, once with the plugin loaded and once without, and reports a per-grader delta between the arms; the delta, not the pass rate, is the measurement (EXT-089). Anthropic's skill best-practices page builds the same step into its five-step loop: run the task without the skill first to find the real gaps, then establish a baseline before writing instructions. LangSmith's published finding shows what a large delta looks like in practice (82% task completion with skills against 9% without, with invocation still only around 70% even when the skill is explicitly prompted); the sweep's verdict was to steal the finding, not the platform. A rule that scores identically in both arms has taught the model nothing, and a suite full of those reports a number that never moves no matter what you write.

Write the cases before the prose. Anthropic's page says it outright: "Create evaluations BEFORE writing extensive documentation," with a checklist requiring at least three evaluations and a pass tested against Haiku, Sonnet, and Opus. The canonical rule for that ordering already lives in `claude-code.md` as part of making a procedure a skill (EXT-038), so this file points rather than restates. Note one staleness in that page as of the sweep: it says "There is not currently a built-in way to run these evaluations," which `claude plugin eval` has since falsified.

The grader ladder comes from the built-in runner's own guidance: "Prefer deterministic graders for long artifacts; llm judges are noisy on long inputs" (EXT-090). It ships six grader types, `regex`, `tool_used` (with `input_match`, `min`, `max`), `tool_order`, `file_exists` (a glob over created paths), `llm`, and `baseline`, and skill invocation is checked with `tool_used: Skill` plus an `input_match` regex rather than with a judge. Anthropic's evals article names the same three classes, code, model, and human, in the same order of preference. `llm-output.md`'s deterministic-backbone rule is this one level up: a fixed code path wherever the steps are knowable, the model only for what you cannot enumerate.

Repeats are not optional for a nondeterministic instrument. `claude plugin eval` defaults to `runs: 3` per case with `--threshold` defaulting to 1.0; skill-creator's `aggregate_benchmark.py` reports mean, stddev, min, and max of pass rate, latency, and tokens; superpowers' own guidance asks for 5-plus repetitions before believing a scenario result (EXT-091). Anthropic's article adds the distinction worth reporting alongside the spread: pass@k (succeeded at least once in k tries) and pass^k (succeeded every time) answer different questions, and quoting one while meaning the other is the eval-tier version of `evals.md`'s rule that one number is never the accuracy.

Then grade the grader. skill-creator's `grader.md` agent does double duty: it grades the run and critiques the eval, flagging assertions that are "too easy to satisfy," and its `run_loop.py` supports a train/test split so a rule is not tuned against the same cases that certify it (EXT-092, PA-036). Anthropic states the human half: "You won't know if your graders are working well unless you read the transcripts," alongside a task-quality bar worth borrowing, that two domain experts should independently reach the same pass/fail verdict on a good task. Two related practices sit at the same layer: pin a cheap model as a canary to find the rule that only works because a large model is smart (superpowers' `run-haiku-test.sh`, and Anthropic's Haiku/Sonnet/Opus checklist), and blind the comparison, unblinding only for analysis, which this fleet already does through `llm-output.md` and its harder-won corollary that blind panels leak through derived fields (PA-039). One point where this module is stricter than anything published: skill-creator has a train/test split, but nobody upstream says what happens after you look at the test set, and `evals.md`'s answer, that a holdout is spent the moment you measure against it and that fact gets recorded, is the rule that keeps an eval suite from quietly becoming a training set.

A final grading preference from the same article, worth stating even though it did not earn its own rule: "It's often better to grade what the agent produced, not the path it took" (EXT-094). The `file_exists` grader globbing over created paths is that preference expressed as a grader type, and this fleet already grades end state in `scripts/lib/retro.mjs` invariants.

Native floor, as of 2026-09-28: the plugin eval runner's ablation mode, which stands up the with and without arms and repeats each case by default, and its grader types, which separate the free deterministic graders from the paid llm and baseline ones (https://code.claude.com/docs/en/plugin-evals; also `claude plugin eval --help`), and the grader material it complements is written up in the skill-creator article (https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills).

## Never let a gate mint the answer key it grades against

repo-a's `match-measurement.md` refuses `--init` together with `--ci` outright: a gate asked to mint the answer key it grades against can only pass. A clean validation run is treated as the moment to check the answer key itself, not as a reason to relax, and no label source gets deference in that check; ranking goes by which verdict is more recent and better evidenced, never by which tool produced it. `project_matcher_eval_state.md` names the incident that forced this: the matcher's first reported 1.00 and 0.87 accuracy figures were self-comparison, not evaluation against hand-labeled data, a fact that was not caught until 2026-07-23; the fixture is now DB-derived and seeded instead. `project_scorer_retune_in_flight.md` (PR #637) shows the same discipline applied to tuning: retune constants are pre-registered in the tool's own header before the sweep runs, measured rather than guessed, with subsequent carryover tracked forward in issue #638. `feedback_pipeline_retro_and_loop_in.md` adds the corpus-side version of the same trap: a proposed guard is validated against labeled data with the corpus assembly checked first, because a corpus that is missing its positives scores every candidate perfectly and that clean score is the failure, not the finding.

A consuming repo's first agent-driven eval (2026-09-30) applied the rule to questions taken from real use: those tasks are scored mechanically, by grounding and attribution checks against the cited document, with no hand-written answer key, and each records whose words the question is. The reasoning is the same as the matcher incident above: a key written for a real question by the people running the eval is the gate grading its own guess, and the first clean score would mean only that the guess and the key agree.

## Report NOT EVALUABLE and NOT MEASURED rather than a fabricated zero

repo-a's `scripts/lib/retro.mjs` carries a `NOT_MEASURED` sentinel with its own origin story in the code comment: a retro once reported `chunks_embedded 218 -> 0` while all 218 embeddings were still sitting in the table, and it read exactly like data loss. A metric present on one side of a delta and absent on the other now prints "(not measured)" with `delta: null` rather than being coerced to zero. `match-measurement.md` makes the same call structural: "a gate has three verdicts, and one is NOT EVALUABLE," after three months of a signal reporting "certain precision 0.0000" before that third verdict existed to describe what was actually happening, which was that the check could not run at all. `council-acquisition.md` reports a real gap the same way: nine image-only meeting scans carry no OCR layer, stated as its own outcome rather than left as a silent absence. `council-meetings.md` states the terse version: "zero samples is a failure, not a pass." repo-b's `lib/plan-okr-sync.mjs` takes the opposite branch deliberately: drift against the OKR planning document is reported as a warning, not a failure, because the local `set.json` worksheet is explicitly labeled "the worksheet, not the source," so a stale worksheet is expected behavior, not corruption. repo-e states the render-side version of the rule: "when a render cannot be completed, say so and reason about the risk explicitly; never imply a check that did not run." An operator memory note extends it to review tooling: treat a verify phase that errored as UNVERIFIED and triage it inline, rather than trusting its empty findings list as if the phase had run clean.

The ruling sentence came from a consuming repo's agent-eval work (issue #111, comment of the same cycle). Two prompt changes were adopted on the same day after null results on the held-out measure, one on cost and one on a confirmed defect, and each was recorded as three separate statements: the measurement, the ruling, and the reason. A null result removes one reason to adopt a change; it does not forbid adopting it, and the record says "adopted by ruling, no measured cost" rather than "improved". The reverse holds for a change rejected after it measured well.

## Show the ratio and the sample, because one number is never the accuracy

`match-measurement.md` requires every published figure to carry its estimand and its sample size, printing `NOT MEASURED` or `NOT EVALUABLE (n=X)` over a hollow number rather than a bare percentage; a capped list under a heading claiming completeness must print the true total and say plainly that it is a sample; the holdout figure and the gold-set precision figure are never quoted against each other, because they answer opposite conditionals and both can be true at once; and blocking recall is measured, not assumed, because a precision fixture is structurally blind to whatever blocking never surfaced in the first place. `build-record.md` states the house style for every number on the public site: "ratios over decimals, sample size always visible; 100% of 110 and 100% of 11 are different claims; a bare decimal never ships." A published data story's README labels its published dataset "floor, not final," because amended campaign filings will move it after publication. repo-e requires a caveat in every score report for the same reason: the score "is a proxy for two real things, retrieval and skim relevance. It is not an ATS pass/fail prediction," attached to the number so it cannot travel without its limits. `feedback_measure_before_modelling.md` states the general form: prefer a measured floor and ceiling to a modelled point, tag anything modelled as modelled, and never compare numbers measured in different units.

The agent-driven form of the rule came from a consuming repo's first eval run (2026-09-30): many questions passed one run and failed the next, so a single run of a question is an example, not a measurement, and the report now shows passes over runs, per model, from more than one run of each question.

The fit-check sentence came from the same consumer (issue #111, comment). A one-paragraph prompt change written after reading one task's transcripts took that task from 0 of 5 to 4 of 5 passing, while the 20 held-out questions showed every difference within noise. The task passing afterwards showed the fix fit the case it was written from; it said nothing about whether the fix generalised. It was scored apart from the held-out cases and reported as "fixes a confirmed defect, no measured cost", not as a gain.

## Make a measuring instrument reproducible

`match-measurement.md` seeds its sampling (`GOLD_SAMPLE_SEED`) so two `--init` runs are byte-identical, on the reasoning that a baseline fingerprint nobody can reproduce means nothing at all. Every PR that touches the matching cascade or its scoring leaves `baseline.json` at the post-PR numbers with the why written in the PR body, because a baseline nobody updates turns the next author's clean run into a phantom regression. A `measurement_staleness` check watches the apparatus itself for staleness, not only the data it measures, and growth in reviewer-corrected labels is read as gold-set decay, not as improvement, since a growing correction count means the key is drifting away from ground truth. The turnout-model data dictionary logs every assumption behind the turnout model with its source and status, so a modelled number can be traced back to what it rests on. repo-d requires a byte-identical parity diff of `out/contacts.scored.json` any time the scoring formula changes, part of its `merge-and-deploy` skill's pre-flight. `project_matcher_eval_state.md` states the fixture-regeneration half of the rule: regenerate a fixture from its source under a seed rather than curate it by hand, and prove the regeneration is byte-identical to the version it replaces. `project_scorer_retune_in_flight.md` (PR #637) adds the holdout-hygiene half: treat a holdout as spent the moment it has been validated against, and draw the next one from labels that have not yet been consumed. `feedback_impact_brief_writing_guide.md` extends the same discipline to prose: tag every load-bearing number with its provenance and commit the exact command that re-pulls it, so a stale figure is a re-run away from being current rather than a rewrite.

Native floor, as of 2026-09-02: `--bare`, which skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md so a scripted run does not vary with ambient config (https://code.claude.com/docs/en/headless); and the session cost figure, computed locally at list price and moved by a `modelPricing` table or a data-residency multiplier without the bill moving (https://code.claude.com/docs/en/costs).

Where bare mode cannot be used, the lean invocation is the receipt. A consuming repo's eval (2026-09-30, Claude Code 2.1.286) authenticates with a subscription login, which bare mode refuses, so it pinned the nearest equivalent: the strict server-config flag, project-only setting sources, an explicit tool list, and the deny-by-default permission mode with an allowlist. Measured once each with a one-word prompt, the unrestricted print-mode session started at about 240,000 cache-creation tokens with 267 tools declared, and the lean one at about 23,000 (n=1 per arm; the model alias in the first run was not honoured, and whether tool deferral was active is not established). The survey carries the method and the caveats as an observed row; the point for the rule is that the difference is large enough to belong in the receipt beside the invocation.

## Evaluate the path a session actually takes

A consuming repo's eval (2026-09-30) scored a tuned single-shot pipeline while everyday sessions went through a different, untuned tool that nothing measured; the strong score described a path nobody took. The same run showed the second half of the rule: a skill instruction that was right for normal sessions sent the eval session to another checkout, and the first fix tried was to edit the skill under test, which would have measured a skill nobody ships. The eval now tells its session about its environment in a system note and leaves the skill alone.

## Deny the eval session what the project allows, and fail a run whose results contain the key

Four failures or measurements from the same consuming repo's run (2026-09-30), each the origin of one sentence of the rule. With project settings loaded, the project's own allow rules reached the eval session, so every project allow the eval does not itself grant is now passed as a deny. A search that named no path got past every Read deny and returned lines from the answer-key directory (the observed rows in `docs/handbook/sources/harness-survey.md`), so a run whose tool output contains the key path now fails, closed, which is detection from results rather than from inputs. A test of the command's rescore path ran the normal path instead and started two real sessions; the test file now replaces the spawn function with one that throws. And a scoring change is re-applied to saved transcripts without re-running sessions, writing beside the original report and never over it, so the earlier number stays comparable and the fix costs nothing.

## Count what the agent did, not only whether it passed

From the same consumer's agent-eval work (issue #111, comment), scoring a retrieval agent through a headless-session eval. The first wording of the fit-checked prompt change offered a text search as an option. Pass rate was unchanged, but proper document opens fell by about a third across 100 runs and shell greps quadrupled. A second wording that fixed this by listing file names only lost the original fix (1 of 5 on the task it was written for): the agent needed the matching line, not a file name, to choose. Only the per-arm tool-call counts showed either effect, so the comparison now prints the mix per arm beside the outcome measures.

## Split a score gap into its causes from the transcripts before building to close it

Two receipts from the same work (issue #111, comment). A gap between "surfaced" and "used" has at least three causes: the agent missed material a good answer needed, the label is broader than a good answer needs, or the measure miscounted. A transcript reading of two 100-run arms found the gap was mostly a source preference the owner then ruled acceptable, plus a measure that counted interchangeable documents as separate targets, which explained a fifth to a third of one gap. Four planned tools had no failure pointing at them and were not built.

The label half: a task logged as "required source not cited" in 7 of 10 runs was, on reading, the agent stating that no such material existed when it did, under different wording. A second always-failing task turned out to be a label problem: the test demanded a refusal where an honest partial answer was correct. A stage label compresses a failure into a few words, and both labels were corrected in the record. The retrieval module's stage-labelling rule (`docs/handbook/retrieval.md`) is the same discipline applied before a label is written.

## Fingerprint what two arms compare, and print every field that differs

Two failures from the same work (issue #111, comment). A text-cleaning pass changed 150 items at an unchanged count and passed the guard that told two corpora apart by counting items, so the guard now fingerprints content and, when a side has no fingerprint, says a same-count change cannot be ruled out. A reviewer found a grouped measure scoring 2.0 out of 1 when both members of an interchangeable group were cited, because one call site was fed the per-file count. The harness version and a fingerprint of the labels in force are recorded per report for the same reason: two arms scored under different versions or labels are not a comparison, and one differing value among ten on a long line was easy to miss until one line named every field that differed.
