# Engineering

## Why this exists

Every rule in this module guards the same failure class: a build that renders fine, exits green, and reports a clean number while being wrong underneath. The bytes on disk say one thing and the served page says another. A gate reports zero and a broken run also reports zero. A config option's name still describes behavior that changed a version ago. None of these failures announce themselves at the point they happen; they surface later, in a different system, read by someone who has to reconstruct what went wrong from a symptom that looks nothing like the cause. This chapter is the incident history behind each rule in `plugins/house/modules/engineering/rules/engineering.md`, drawn from five repos that hit the same failure shapes independently.

## Build the simplest thing that answers the question

repo-b's `/new-tool` command (`.claude/commands/new-tool.md`) scaffolds a public tool by putting pure logic in `src/lib/` before the Astro page exists, on the stated rationale that "untested logic buried in a template is what the procedure exists to prevent." Its `console/app.md` rule makes offline development the default posture for the client half: a mocked API, no live Neon connection required for the common path. An operator memory note (`feedback_measure_before_modelling.md`) records the same instinct from the other direction: check whether the platform already measures the thing directly before building a model of it, and prefer a measured floor and ceiling to a modelled point. Anthropic's own building-effective-agents guidance backs both calls: add complexity only when it demonstrably improves outcomes, and consolidate near-duplicate tools rather than let them proliferate and burden the reader deciding which one to pick. The same restraint has a documented default for diagrams (EXT-019): draw the C4 context and container levels and stop there unless a component view earns itself, since the levels are progressive zoom rather than a set you owe anybody. One honest caveat travels with that: c4model.com describes the levels but does not itself say to stop at containers, so the stopping rule is widely-held community practice rather than documented guidance, and it is recorded here as such.

## Keep one implementation per computation, and let the gate and the report share it

repo-a's `check:equal-treatment` gate and its retro report both read from `scripts/retro/domains/content.mjs`: "the comparison logic lives in the retro domain, not duplicated, so the gate and the retro can never disagree about what the rule means." The same repo's build-record chapter gates a number appearing on a diagram exactly like the same number in prose, and its DB layer derives return types as `z.infer<>` of the Zod schemas so `tsc --noEmit` fails on column drift instead of a hand-typed type silently going stale. An operator memory note (`feedback_newsletter_two_renderers.md`) names the incident this rule exists to prevent: one newsletter issue JSON feeds two renderers, `newsletter/[slug].astro` and `lib/newsletter.ts`, and a new shell field wired into only one of them is silently dropped by the other on render.

## Prove a check can fail before trusting that it passed

repo-a's finance-pipeline reload check carries its own founding incident: testing it right after a load should report zero, but zero is also what a broken run reports. The first cut aliased columns `AS tran_namF`, Postgres folded the identifier to lower case, every row reconstructed to an empty name, and the run printed a tidy zero that looked exactly like success. The fix validates with both halves, a known-answer case that must be non-zero and the no-op case that should be zero. repo-b keeps a matching discipline: `brain/retrieval.md` runs an eval yardstick (`brain/evals/questions.yaml`) through `npm run kb:eval` before trusting a retrieval batch, and `lib/plan-okr-sync.mjs` backs a fallible prose instruction (don't let a plan revision drift from its worksheet) with a machine check that reports every value that moved between revisions. Operator memory carries the sharpest statement of the rule (`feedback_no_op_is_not_evidence.md`): a tool reporting zero changes is not evidence it works, because a broken tool can be broken in exactly the way that always reports zero; pair the no-op case with a case whose answer is known independently, and ask what a totally broken version would have printed before believing a clean pass. A related note (`project_css_diff_harness_traps.md`) makes the positive control concrete: perturb one value, confirm the harness reports it, revert, before trusting any zero-delta result from the same harness. `project_donor_dedup_fixtures.md` turned two real surfaced clusters, a 4-variant company-name cluster and a 3-variant acronym-variant cluster, into the acceptance tests for the donor-dedup tool rather than leaving the finding as a one-off note.

Native floor, as of 2026-09-02: the plugin eval runner's automatic no-plugin baseline arm (`--ablation with-without`), which scores one arm against another and so measures a rule's effect rather than proving the check itself can still fail. The runner has no public docs page as of that date; the behavior is documented only in `claude plugin eval --help` (https://code.claude.com/docs/en/plugins-reference.md carries no eval material), and the practice it complements is written up in Anthropic's evals article (https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

## Verify the served artifact, not the source

repo-a's `check:images` gate exists because of PR #549: a Cloudflare adapter change silently switched what `imageService: 'compile'` selected between majors while the config comment kept describing the old behavior, and every candidate portrait shipped for months as the original PNG under a hashed `.webp` name. No amount of reading the config would have caught it; only the bytes would. `scripts/check-image-optimization.mjs` now reads every emitted variant under `dist/client/_astro/` for two independent things, real format (magic bytes match the extension) and real shrink (at least the `MIN_SHRINK` threshold smaller than its source), because either check alone misses a different failure: format alone misses a real-but-useless encode, shrink alone misses a format that happens to compress. repo-c's `CLAUDE.md` states the same discipline as a merge gate: "show the real data before merging anything that changes a report," run the dev server, open the affected page, check it by hand against the source workbook, because a report that renders beautifully and is quietly wrong is the failure that actually matters. Operator memory carries the front-end half of the same lesson repeatedly: grep the built output for the literal after any value sweep, not the source construct (`feedback_grep_built_output_not_source.md`); count rules in the built artifact, not the source files, before asserting a front-end defect (`feedback_verify_rendered_not_source.md`); prove a no-visual-change claim with a computed-style diff across pages and widths (`feedback_prove_no_visual_change.md`); test a rendering a desktop preview structurally cannot reproduce on the real client before it ships (`feedback_broadcast_phone_testsend.md`); and answer an "any updates" question by querying the upstream county feed directly, never a cached read of it (`feedback_check_county_directly.md`). repo-e's render-verification rules (`resume_instructions.md:19`, ruled 2026-08-10) generalize the same instinct to a desktop app: "a page count is not a render check," because a PDF export tool exports the document that happens to be active in the word processor, not necessarily the file just handed to it; every render is instead verified by asserting a distinctive tailored phrase is present and the prior record's phrase is absent, with whitespace normalized on both sides first so a line wrap can't defeat the probe.

## Validate the body before writing it, because a status code is not a content check

repo-a's `council-acquisition.md` states the rule that everything else in that pipeline follows from: every host it fetches from answers a request it cannot serve with a valid-looking page under HTTP 200. Trusting the status code archived 39 identical error pages before anything noticed, "the same lesson `check:images` exists for: the name was not evidence, only the bytes were." `fetchAndArchive` now takes a `validate(body)` that runs before anything touches disk. A rejection writes neither the artifact nor its ledger row, because an orphan file with no row pointing at it is invisible on both axes, nothing looks for a file that no row claims. Three consecutive refusals for one kind abandon that kind for the run, so a wrong URL costs three requests rather than thirty-nine. A separate incident (`project_jsonb_double_encode.md`) is the same rule applied to a database write: `${JSON.stringify(obj)}::jsonb` through the repo's `sql` tagged-template wrapper stores a jsonb *string*, not a jsonb value, and the fix is to read the stored column's type back after any scripted write to a structured column, before a consumer is built on top of it.

## Never let a gate mint the answer key it grades against

repo-a's `match-measurement.md` refuses `--init` together with `--ci` outright: a gate asked to mint the answer key it grades against can only pass. A clean validation run is treated as the moment to check the answer key itself, not as a reason to relax, and no label source gets deference in that check; ranking goes by which verdict is more recent and better evidenced, never by which tool produced it. `project_matcher_eval_state.md` names the incident that forced this: the matcher's first reported 1.00 and 0.87 accuracy figures were self-comparison, not evaluation against hand-labeled data, a fact that was not caught until 2026-07-23; the fixture is now DB-derived and seeded instead. `project_scorer_retune_in_flight.md` (PR #637) shows the same discipline applied to tuning: retune constants are pre-registered in the tool's own header before the sweep runs, measured rather than guessed, with subsequent carryover tracked forward in issue #638. `feedback_pipeline_retro_and_loop_in.md` adds the corpus-side version of the same trap: a proposed guard is validated against labeled data with the corpus assembly checked first, because a corpus that is missing its positives scores every candidate perfectly and that clean score is the failure, not the finding.

## Report NOT EVALUABLE and NOT MEASURED rather than a fabricated zero

repo-a's `scripts/lib/retro.mjs` carries a `NOT_MEASURED` sentinel with its own origin story in the code comment: a retro once reported `chunks_embedded 218 -> 0` while all 218 embeddings were still sitting in the table, and it read exactly like data loss. A metric present on one side of a delta and absent on the other now prints "(not measured)" with `delta: null` rather than being coerced to zero. `match-measurement.md` makes the same call structural: "a gate has three verdicts, and one is NOT EVALUABLE," after three months of a signal reporting "certain precision 0.0000" before that third verdict existed to describe what was actually happening, which was that the check could not run at all. `council-acquisition.md` reports a real gap the same way: nine image-only meeting scans carry no OCR layer, stated as its own outcome rather than left as a silent absence. `council-meetings.md` states the terse version: "zero samples is a failure, not a pass." repo-b's `lib/plan-okr-sync.mjs` takes the opposite branch deliberately: drift against the OKR planning document is reported as a warning, not a failure, because the local `set.json` worksheet is explicitly labeled "the worksheet, not the source," so a stale worksheet is expected behavior, not corruption. repo-e states the render-side version of the rule: "when a render cannot be completed, say so and reason about the risk explicitly; never imply a check that did not run." An operator memory note extends it to review tooling: treat a verify phase that errored as UNVERIFIED and triage it inline, rather than trusting its empty findings list as if the phase had run clean.

## Show the ratio and the sample, because one number is never the accuracy

`match-measurement.md` requires every published figure to carry its estimand and its sample size, printing `NOT MEASURED` or `NOT EVALUABLE (n=X)` over a hollow number rather than a bare percentage; a capped list under a heading claiming completeness must print the true total and say plainly that it is a sample; the holdout figure and the gold-set precision figure are never quoted against each other, because they answer opposite conditionals and both can be true at once; and blocking recall is measured, not assumed, because a precision fixture is structurally blind to whatever blocking never surfaced in the first place. `build-record.md` states the house style for every number on the public site: "ratios over decimals, sample size always visible; 100% of 110 and 100% of 11 are different claims; a bare decimal never ships." A published data story's README labels its published dataset "floor, not final," because amended campaign filings will move it after publication. repo-e requires a caveat in every score report for the same reason: the score "is a proxy for two real things, retrieval and skim relevance. It is not an ATS pass/fail prediction," attached to the number so it cannot travel without its limits. `feedback_measure_before_modelling.md` states the general form: prefer a measured floor and ceiling to a modelled point, tag anything modelled as modelled, and never compare numbers measured in different units.

## Make a measuring instrument reproducible

`match-measurement.md` seeds its sampling (`GOLD_SAMPLE_SEED`) so two `--init` runs are byte-identical, on the reasoning that a baseline fingerprint nobody can reproduce means nothing at all. Every PR that touches the matching cascade or its scoring leaves `baseline.json` at the post-PR numbers with the why written in the PR body, because a baseline nobody updates turns the next author's clean run into a phantom regression. A `measurement_staleness` check watches the apparatus itself for staleness, not only the data it measures, and growth in reviewer-corrected labels is read as gold-set decay, not as improvement, since a growing correction count means the key is drifting away from ground truth. The turnout-model data dictionary logs every assumption behind the turnout model with its source and status, so a modelled number can be traced back to what it rests on. repo-d requires a byte-identical parity diff of `out/contacts.scored.json` any time the scoring formula changes, part of its `merge-and-deploy` skill's pre-flight. `project_matcher_eval_state.md` states the fixture-regeneration half of the rule: regenerate a fixture from its source under a seed rather than curate it by hand, and prove the regeneration is byte-identical to the version it replaces. `project_scorer_retune_in_flight.md` (PR #637) adds the holdout-hygiene half: treat a holdout as spent the moment it has been validated against, and draw the next one from labels that have not yet been consumed. `feedback_impact_brief_writing_guide.md` extends the same discipline to prose: tag every load-bearing number with its provenance and commit the exact command that re-pulls it, so a stale figure is a re-run away from being current rather than a rewrite.

Native floor, as of 2026-09-02: `--bare`, which skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md so a scripted run does not vary with ambient config (https://code.claude.com/docs/en/headless); and the session cost figure, computed locally at list price and moved by a `modelPricing` table or a data-residency multiplier without the bill moving (https://code.claude.com/docs/en/costs).

## Assert an invariant where its state is created, with a why and a remedy

repo-a's `scripts/lib/retro.mjs` defines a domain's invariants as `{key, severity, title, why, remedy, check(ctx)}`, with `why` and `remedy` required fields, "because the person reading a failure at 11pm should not have to rediscover either." A `severity: 'hard'` violation exits non-zero through `hasHardFailure`, so bad state cannot flow downstream to a publish or a deploy. The framework's own origin story is the argument for writing invariants at all: the first one ever written, catching two people sharing a voter registrant, surfaced not where the bad state was created but as an unrecognizable `ON CONFLICT DO UPDATE command cannot affect row a second time` error inside a different repo's sync, two systems downstream from the actual cause. `.claude/rules/enrichment.md` applies the same shape to a cost constraint: the pipeline's cost-zero invariant is named explicitly (don't add `ANTHROPIC_API_KEY` to the workflow or scripts) so a well-intentioned automation change cannot quietly start spending without anyone deciding to allow it.

## Make every waiver print its reason, and give an integrity gate none

repo-a's `check-equal-treatment.mjs` accepts `EQUAL_TREATMENT_WAIVER="<reason>"` to downgrade a failure to a loud warning for exactly one run, requiring a non-empty reason that gets printed, and is deliberately awkward to use: "a waiver should be a decision someone makes out loud, not a flag that lives in a script." Its paired `source_ref_integrity` invariant, the one that keeps a footnote pointed at the source it was written against, gets no waiver at all and short-circuits before the waiver prompt is even reached, so a citation-integrity failure can never be papered over by that mechanism. The same reason-carrying shape recurs across the repo as a convention rather than a one-off: `GOLD_DRIFT_ACCEPT="<reason>"`, `SWEEP_BASELINE_ACCEPT="<reason>"`, and `DEPLOY_FROM=any` all require and print a reason before they let anything through.

Native floor, as of 2026-09-02: a PreToolUse hook denial, which applies in every permission mode, including bypass, but demands no reason from the person overriding it and scopes nothing to a single run (https://code.claude.com/docs/en/hooks.md).

## Read a missing field as missing, because absence is not confidence

repo-a's `match-measurement.md` describes the incident directly: a check once tested `v.confident === false`, which passed a verdict that had merely omitted the `confident` field, silently collapsing "the reviewer said no" and "the reviewer didn't say" into the same reading. The fix reports an explicit `false` and a missing value as two different outcomes everywhere a reviewer packet is read, on the stated principle that "said nothing is not said yes."

## Demote a gate that has been wrong before

repo-e's `scripts/check_pagefit.py` is the source of this rule. Its char-over/bullet-under combination has rendered both ways in past runs: a 12-bullet draft against a 14-bullet anchor spilled to two pages, while two other drafts reading the same way over budget still rendered one page. Rather than trust that the check has quietly self-corrected, that blind spot is documented in the tool itself, with the observed cases kept as a running record rather than discarded, and the checker prints its own verdict as advisory rather than authoritative on that specific combination: "treat the verdict as advisory and let the Word render decide. Do not cut content on this signal alone." A gate that has been wrong before does not get to be certain until that record earns it back.

Native floor, as of 2026-09-02: hosted Code Review reports its findings on a check run that never blocks a merge and filters candidates through a verification pass before posting them, and only where that Team and Enterprise preview runs (https://code.claude.com/docs/en/code-review.md#check-run-output).

## Record a significant decision as a numbered, immutable record

repo-e's `conflict_ledger.md` (1,193 lines) keeps one dated, numbered ruling per fact. A ruled value is canonical; every other variant of that fact becomes historical only, and an unruled item stays flagged and blocked from output. Superseding is written into the record itself rather than an edit to the original: `~~Title~~ superseded by ruling 16 (2026-07-22)`. This fleet's own decision records, and repo-e's ledger, both trace to the same external convention (adr.github.io, and MADR 4.0.0 for the template shape): record each architecturally significant decision as a numbered, immutable file; never edit a decided record, supersede it with a new one and mark the old one superseded; keep each record short on a standard template so writing one stays part of normal flow rather than a special occasion; and write a record only for a decision with measurable architectural effect, since a record for every minor choice devalues the set until nobody reads any of them. That last clause is contested, not settled, and the disagreement is the practice worth carrying (EXT-073): adr.github.io restricts a record to an architecturally significant decision, while MADR explicitly extends the same format to any significant decision, architecture or not. The two readings pull in opposite directions, and a package that quotes only one of them hides the choice it made. This repo uses MADR's template with adr.github.io's admission bar, which is a deliberate mix: the broader format, kept for the narrower set, so writing a record stays cheap without the set growing until nobody reads it.

Native floor, as of 2026-09-02: auto memory, which stores notes machine-local outside the repo and rewrites them in place, so nothing native gives a decision a number, an immutable body, or a supersession marker (https://code.claude.com/docs/en/memory).

## Land a build-time guard with the code it protects

repo-a's nine retro domain modules each open by naming the specific failure class they exist to catch, not a generic description. `council.mjs` states it plainly: "the failure this domain exists to catch is quiet and publishable... every hard check below is something that would render fine and be wrong." The repo's `package.json` lifecycle runs guards before generators, with the one check that needs the build's actual output, image optimization, placed in `postbuild` where the bytes finally exist to check: `prebuild` runs `check-docs-drift`, `check:build-record`, and `check:equal-treatment` before any generator writes a file; `build` runs the Astro build; `postbuild` runs `check-image-optimization`. `CLAUDE.md` states the reason shared by all three: "a class of failure that renders fine, builds green, and is invisible to review." repo-c's `CLAUDE.md` carries the same convention one step earlier, for guards that don't exist yet: a `Build-time guards` section names two future guards and the exact silent failure each will prevent, with the rule stated as a commitment rather than a plan: "they land with the code they protect, not before."

## Search public prior art before building a tool, and record what you did not adopt

repo-e's `reviews/2026-07-24-writing-efficacy-review.md` is the one recorded incident behind this rule: a fresh-eyes review of the system judged it "first against the repo's own rules, then calibrated against current external guidance," with sources listed at the bottom of the review rather than left implicit, under a stated hybrid protocol where mechanical fixes land directly in that commit and everything judgment-level ships instead as a proposal that waits on the operator's approval.

Native floor, as of 2026-09-02: plan mode, which holds edits until a person approves a plan except in sessions where bypass permissions are available, and which leaves no record once the plan is approved (https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode).

## Pin a framework default your output depends on, with the reason beside it

repo-a's `check-image-optimization.mjs` justifies its `MIN_SHRINK` constant (0.25) in a comment beside the value: portraits land around a 95% shrink in practice, so 25% is low enough to never fire on a genuinely hard-to-compress image, and high enough that a 0% passthrough still cannot sneak past it. `vitest.config.mjs` carries a 15-line comment on its `oxc: { jsx: ... }` setting, explaining why the older `esbuild.jsx` spelling is silently ignored and why fixing the setting centrally beats a scoped `tsconfig` per template directory: "that is not hypothetical: it broke the three email suites on the Astro 7 upgrade." A CI workflow's `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: 'true'` flag carries both the deprecation link and a note that it becomes a no-op, and removable, once Node 24 is the runner default. A Cloudflare vendor quirk, a pinned `[[kv_namespaces]]` block, carries its mitigation and the cost of removing it directly in the config: don't drop that block, or deploys will fail again. repo-d's `.gitignore` explains every non-obvious anchored rule in a comment, for example why `/public/` (anchored) rather than a blanket `public/`, because a sibling app's `app/public/` is Vite's own source `publicDir` and would otherwise be swept up by the same pattern. This is the same rule Anthropic states for agent-facing configuration, the "voodoo constants" ban: justify every configuration constant in a comment, because if the person writing the value doesn't know why it's right, neither will the agent reading it later.

## Enumerate from the system of record, and fail hard on a missing member

An operator memory note (`feedback_no_carve_outs_on_removal.md`) records the incident behind this rule: told to remove something, an agent that removes it from the obvious place but leaves it standing in a sibling surface has not actually removed it, and the gap does not announce itself. The remedy is procedural rather than a reminder to be thorough: enumerate every surface, source and built output together, in one pass, with no carve-outs decided in advance.

## Normalize against fixed anchors, never against the live population

repo-a's `build-record.md` states the rule as a check on any published share: state it on a denominator that could plausibly have produced the numerator, and hold that denominator fixed rather than letting it drift with a live population. Where part of the pool is structurally ineligible, for example already decided, out of scope, or withdrawn, subtract it explicitly, or say plainly that the published figure did not.

## Make an error message teach the fix

repo-a's `scripts/lib/assert-master-at-origin.mjs` traces its own origin to PR #205, where a Tier 1 carve-out met stacked work already sitting in the master checkout and the mismatch was hard to diagnose from the resulting error. On refusal it now prints the working directory, both SHAs (HEAD and `origin/master`), and three labeled remediations, one of them a transient-worktree recipe, rather than a bare "not on master." `src/lib/db/client.ts` fails fast, refusing to start, on a missing `DATABASE_URL`: "by design; silent fallbacks would ship stale content" instead of a clear failure. The repo's `database.md` and `design.md` gotchas sections record the symptom beside the fix for each stack-specific trap (a `.astro` template-body generics error that reports 200 lines off from the real cause, generated columns rejecting `UPDATE`, a partial unique index needing its predicate echoed on `ON CONFLICT`), so the next reader recognizes the failure before diagnosing it from first principles. Anthropic's own tool-writing guidance states the general form of the same rule: make an error message teach the fix rather than only report the failure, so an agent's retry has somewhere useful to go.

Native floor, as of 2026-09-02: hook exit-code semantics, which pass a blocking hook's stderr, or its JSON reason, back to the agent verbatim and never require it to say anything useful (https://code.claude.com/docs/en/hooks.md).

## Read config from the environment, and keep build, release, and run separate

No incident recorded; the rule came in on reasoning alone, from the 12-factor app conventions (config, build-release-run, dev-prod-parity). Store all config in environment variables, on the litmus test that the repo could be published open source at any moment without leaking a credential. Avoid named config groups (`development`/`staging`/`production`), because they multiply combinations and make deploys brittle rather than simpler. Separate build, release, and run strictly, give every release a unique ID, and never mutate a release once it exists, since an append-only release ledger is what makes rollback possible at all. Keep the run stage simple even when the build stage is complex, because a runtime failure happens when nobody is watching, unlike a build failure that happens in front of whoever triggered it. Resist different backing services between development and production, even from behind an adapter meant to hide the difference, because that gap is exactly where "passed in dev, failed in prod" comes from.
