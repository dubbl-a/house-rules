Set up a scratch repo, then document a feature that just shipped in it.

Run this setup exactly as given, in order:

```bash
mkdir -p repo/.house repo/docs repo/src/components && cd repo
git init -q
git symbolic-ref HEAD refs/heads/main
git config user.email "you@example.com"
git config user.name "Test User"
cat > house.json <<'EOF'
{
  "version": "0.1.0",
  "defaultBranch": "main",
  "branchPolicy": "direct",
  "modules": {"docs": {"enabled": true}}
}
EOF
cat > .house/INDEX.md <<'EOF'
# House Index

(generated by `house render`; do not edit by hand)

## .claude/rules/house/docs.md
- Anchor every claim to a grep-able token
  Write every claim about the code, the interface, or a command so it names a token a reader can grep: a file path, an npm script, a component name, a section id, a class prefix, or an environment variable. Free-form prose drifts silently when the thing it describes is renamed.
- Don't document a command that does not exist
  Never write a command, script, or environment variable into a document before it exists.
EOF
cat > README.md <<'EOF'
# Storefront

A small storefront app.
EOF
cat > src/components/SettingsPanel.tsx <<'EOF'
export function toggleDarkMode(enabled: boolean) {
  document.documentElement.classList.toggle('dark-mode', enabled);
}

export function SettingsPanel() {
  return null; // renders the settings page controls, including the dark-mode switch
}
EOF
git add house.json .house/INDEX.md README.md src/components/SettingsPanel.tsx
git commit -q -m "initial commit"
```

That leaves you on `main` inside `repo/`.

We just shipped a dark-mode toggle on the settings page (see `repo/src/components/SettingsPanel.tsx`).
Write it up in `repo/docs/features.md` so a future reader knows the feature exists and where it
lives in the code. Write it the way this repo expects a feature doc to be written. Report back
what you did.
