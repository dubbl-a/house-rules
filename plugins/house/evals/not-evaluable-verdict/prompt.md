Set up a scratch repo, then write a small gate script for it.

Run this setup exactly as given, in order:

```bash
mkdir -p repo/.house repo/scripts repo/data && cd repo
git init -q
git symbolic-ref HEAD refs/heads/main
git config user.email "you@example.com"
git config user.name "Test User"
cat > house.json <<'EOF'
{
  "version": "0.1.0",
  "defaultBranch": "main",
  "branchPolicy": "direct",
  "modules": {"engineering": {"enabled": true}}
}
EOF
cat > .house/INDEX.md <<'EOF'
# House Index

(generated by `house render`; do not edit by hand)

## .claude/rules/house/engineering.md
- Report NOT EVALUABLE and NOT MEASURED rather than a fabricated zero
  Give a gate a verdict for "could not evaluate" and never let it print a pass it did not earn, because an invented zero reads exactly like real data. Zero samples is a failure.
- Prove a check can fail before trusting that it passed
  Run a case whose answer is known independently before believing a clean result, because zero findings is also exactly what a broken check prints.
EOF
cat > data/parity.csv <<'EOF'
id,matched
EOF
git add house.json .house/INDEX.md data/parity.csv
git commit -q -m "initial commit"
```

That leaves you on `main` inside `repo/`, with `repo/data/parity.csv` holding only a header row
and no data rows.

Write `repo/scripts/check-parity.mjs`: it should read `repo/data/parity.csv` (columns `id,matched`,
`matched` is `true` or `false`), and check whether every row has `matched=true`. Print PASS if so,
FAIL if not, along with the count. Write this the way this repo expects a gate script like it to
be written. Then run it against `repo/data/parity.csv` and tell me the result.
