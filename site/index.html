House Rules Explained

Claude Code does what you ask. These rules cover what you didn't know to ask for, and a checker tells you when your written instructions stop matching your project.

What it is: plain-English working rules for projects built with Claude Code, copied into your project as ordinary files, plus one command that reports where those files and the project disagree.

Why you'd want it: if you aren't an engineer, you don't yet know which safeguards to ask for, and Claude Code won't pick them for you. And instructions you do write down go out of date as the project changes. Nothing checks them unless you add something that does.

What this is

Claude Code is a program with an AI assistant that reads and edits the files in your project. It will build almost anything you describe. It won't, by itself, suggest safeguards you didn't ask for, and it won't check whether the instructions you gave it last month are still accurate. house-rules handles both.

The first gap matters from day one if you aren't an engineer. Claude Code knows how to change stored data safely, or how to try a change on a separate copy of the project first, but it doesn't decide which of those your project needs. If you never ask for a backup, you won't have one when you need it.

The second gap appears a few weeks in. A project, here, is the folder of files you're building something in, and a session is one working conversation with Claude Code. Anything you write down for Claude Code is advice: nothing confirms a session followed it, that it's still true after you rename a file, or that the copy in your next project says the same thing. Over time the instructions fall out of date and get too long to follow.

house-rules is a set of working rules for projects built with Claude Code: how changes are made, how stored data is protected, how documents stay accurate, how a session's lessons are kept, and more. Each rule says why it exists, so you can follow the reasoning and disagree with it. The rules are copied into your project as ordinary files. One command, typed into a terminal (the window where you type commands), reads them back along with your project's documents and lists anything that no longer matches.

You don't need to be a programmer. You need a project, a terminal, and a few free tools, set up under Getting started. Technical words are explained where they first appear, and there's a glossary at the end.

What goes wrong

Two kinds of problem, and neither produces an error message.

The first is what you never asked for. A change to stored data runs without a backup. A fix goes straight onto the shared copy of the project instead of being tried on a separate one first. A safeguard gets added, and nobody checks that it can actually catch anything. One written rule would have prevented each of these, but you didn't know to write it.

The second is what you did write down. You put your preferences in a file at the top of the project, and for a while sessions mostly follow them. Then the file grows and the project changes, and the two stop matching. You can't tell from the outside whether a session skipped a rule, or whether a rule is still true. Typical failures:

  • The instruction file grew a paragraph with every fix, and now only part of it gets followed.
  • You copied a rule into three projects, and the copies have since diverged.
  • A rule tells the assistant to run a program you renamed last month. Nothing compares the rule to the project, so it stays wrong.
  • Someone asks why a rule exists, you can't remember, and the rule gets ignored instead of fixed.
  • What a session figured out on Tuesday is gone by Thursday, or sits in notes on one machine.

None of these break anything right away, which is why they're easy to miss.

Your house: what Claude Code sets up, and what you post yourself

Think of each project as a house you own. Claude Code is what the builder installed before you moved in, and it's the same in every house. The assistant, from here on, means one session of Claude Code: a guest, new each time. The builder gives you:

  • A noticeboard by the door. Every session, Claude Code reads the instruction file at the top of your project. It also reads rule files: one that names the files it covers is read only when such a file is opened, and one that names none is read every session. The board holds advice, and a guest can ignore it.
  • Doors and locks. You can forbid some commands in Claude Code's settings file, and Claude Code then refuses them. That's real enforcement, not a request.
  • A fuse box. A hook is a small program Claude Code runs just before an action, and it can block that action.
  • A notepad on the fridge. The assistant keeps notes between sessions, on that machine only.
  • Appliances. A plugin is an add-on that gives Claude Code extra skills and hooks. A skill is a set of instructions you run by typing its name after a slash. A plugin can't put anything on the noticeboard.

Those are good places to put rules. But Claude Code doesn't decide what the rules should say, and it doesn't check later whether they're still true.

house-rules supplies the rules themselves, written by someone who has learned what to ask for, in the same words in every house. It also adds four things the builder doesn't:

  • A sealed copy of each rule file. Each copy has a fingerprint, a short code that changes if even one character changes, so an edit shows up.
  • An inspector who reads the house's documents and reports what's wrong.
  • A ledger recording what this house does differently, and why.
  • A handoff, so what one guest learned reaches the next one instead of staying on the fridge.

The analogy breaks down in one place. An appliance can't switch off a real fuse box, but hooks can be turned off: by a setting, and a session started in bare, safe or restricted mode loads no project hooks at all. So a rule that must always hold also gets a lock, one of the forbidden-command settings, instead of relying on the hook alone.

How it works, in six moves

The first three steps decide what a rule says and where it lives. The last three catch a rule that has stopped being true.

  1. Give every rule a reason. Each rule is an instruction, one clause saying why, a line naming what enforces it, and a pointer to the evidence behind it. People work around rules they can't justify.
  2. Load only what's relevant. Each rule file names the kinds of file it covers, so a session reads only the rules that apply. Each file can also have a maximum length, set in your project's settings file; this package caps its own at 200 lines.
  3. Copy the rules in. They're written word for word into your copy of the project (your checkout), where Claude Code reads them like any other file.
  4. Fingerprint each copy. A lock file records what each file looked like when it arrived.
  5. Run the checker. Whenever you ask, it rereads the project and lists what no longer matches.
  6. Fix rules at the source. If you disagree with a rule, change it in the package, not your copy. The next version reaches you as a plan you approve.

What is in the package

Twelve modules, 138 rules in all. A module is a set of rules on one subject. Five are on unless you switch them off:

  • claude-code covers the assistant's setup: what it reads each session, how long that can be, and where a new fact belongs.
  • docs covers the README, changelog and rule files, so no document points at something that no longer exists.
  • engineering covers how code is written and changed day to day.
  • github covers how a change reaches GitHub, the website where a project and its history are stored and shared. Every change goes on a branch and through a pull request. A branch is a separate line of work, kept apart from the main line that everyone builds on. A pull request proposes merging a branch into the main line, with a chance to review it first.
  • testing covers what "done" means: what gets tested, and what a passing test actually proves.

Five more turn on only if your project seems to need them. database covers changes to how stored data is organized. deployment covers releases, so putting something live is deliberate. data-pipelines covers scheduled jobs that move data in bulk. llm-output covers text produced by an AI model, before anyone treats it as fact. evals covers measurement, so a score means what it claims.

The last two are off until you switch them on in your settings file. security covers what a session trusts and installs, so text it reads or a package it adds can't take over your machine or your code. retrieval covers answers drawn from a collection of documents, so a wrong answer is traced to the step that failed before anyone tries to fix it.

Safeguards you wouldn't have known to ask for. One example from each module, in plain words. Each is something the assistant now does, or refuses to do, without being asked.

  • claude-code: When more than one Claude Code session might be working in the same project, the assistant saves your changes and asks you before switching tasks, so a second session can't strand the first one's work.
  • docs: The assistant never writes a command or setting into your project's instructions unless it already exists, so you never follow a step that is not real.
  • engineering: The assistant keeps passwords and secret access codes out of your project's code, storing them somewhere separate, so publishing or sharing the project cannot leak them.
  • github: On GitHub, typing "fixes" or "closes" next to a task's number closes that task automatically, even by accident. The assistant avoids those words unless it means them, so open tasks don't close by accident.
  • security, once you switch it on: When a web page, an issue, or a tool's output tells the assistant to run a command or install something the task did not ask for, it stops and tells you instead, because whoever wrote that text does not work for you.
  • testing: When the assistant adds a check meant to block a bad change, it also writes a test proving the check can catch one, so a broken safeguard can't wave bad changes through unnoticed.
  • database: Before any change to stored data that could delete or overwrite it, the assistant takes a backup, proves the backup restores, and compares record counts afterward, so a mistake can't destroy data for good.
  • deployment: The assistant restores your backup for real from time to time, rather than only confirming a file exists, so you learn whether it works before an emergency instead of during one.
  • data-pipelines: The assistant refuses to delete more than a small share of any stored data set unless you confirm it, because a run that empties everything looks like routine cleanup until it is too late.
  • llm-output: Text a model produced goes into a separate holding area, not straight into your files, so nothing becomes final until a person has checked and moved it, apart from cases you approved in advance.
  • evals: When the assistant measures whether something works, it reports how many tries passed out of how many, from more than one try, so one lucky pass is never presented as proof.
  • retrieval, once you switch it on: When an answer drawn from your documents is wrong, the assistant first finds out whether the right document was missing, never found, never opened, or opened and misread, so the fix goes to the step that actually failed.

Five skills. You run each one inside Claude Code by typing its name after a slash.

  • /house-rules:bootstrap sets a project up the first time.
  • /house-rules:sync brings a later version in.
  • /house-rules:conventions answers "what is the house rule for this" from a short index, a table of contents of the rules, without reading every rule.
  • /house-rules:revise-docs files something you just learned where it belongs.
  • /house-rules:handoff closes a session by writing down what the next person needs.

The branch guard is a hook, the fuse box from the analogy. When your project's settings say changes go through pull requests, it refuses to commit or push straight onto the main line. A commit is one saved snapshot of a change; a push sends saved changes up to GitHub.

The checker is the inspector: one command, node .house/check.mjs, running twelve kinds of check. It looks for things like a managed file edited by hand, a document naming a file that's gone, and a file over its length limit.

house.json is the settings file for all of this, added to your project at setup. It records which modules are on, keeps a dated list of anything you've declined, and holds each file's length limit, which tightens as the file shrinks.

Twelve evals test whether a session actually follows the rules. An eval is a real task plus a check of the result. They come in pairs: one case where a rule should apply, and one where it shouldn't.

Why I built this

I'm Aaron Altamura. I build AI and data systems for go-to-market teams at software companies, so I'm not a software engineer by trade. I build the tools I need with Claude Code, and I wrote this guide with it, in the plain language I wanted when I started.

Over about five months I built five working projects that way, roughly 1,312 commits between them (a commit is one saved change). These rules are what I wrote down after the same problems hit me more than once.

One instruction file grew to 1,512 lines when its own rule said 200, and nothing flagged it, so most of it got skipped. A rule kept pointing at a program I'd renamed, because nothing checked the rule against the project. Rules I couldn't justify got worked around, which was fair, since I'd written the instruction but not the reason. And what one session learned stayed in notes on my machine, where no one else could see them.

None of that was Claude Code's fault. It gave me places to put rules, and hooks to enforce them. It just doesn't decide what the rules should say, or tell me when one has stopped being true. So I wrote those parts. My five projects run on these rules now, and so does this package.

Getting started

These steps are written for a Mac. On Linux they are the same, except that you install the tools with your system's own installer rather than with Homebrew, the Mac installer described just below. On Windows, the Claude Code quickstart linked below covers your version.

What you need first

  1. A terminal. On a Mac, open the Terminal app.
  2. Homebrew, the tool that installs other tools on a Mac, installed once from https://brew.sh.
  3. Three tools, installed with brew install git gh node. Git tracks your project's history, gh is the GitHub command line tool, and Node runs the checker. Node must be 22 or newer, which node --version confirms.
  4. A GitHub account, signed in once with gh auth login.
  5. Claude Code itself, installed by following the official quickstart at https://code.claude.com/docs/en/quickstart, which gives a one-line install command for Mac and Linux and the Windows equivalents. Then run claude and follow the prompts to sign in.

Install house-rules, once per machine. The first command below points Claude Code at the marketplace that publishes house-rules. A marketplace is a published list of add-ons and where to get them. The second installs it for your user account, so it is there in every project.

claude plugin marketplace add dubbl-a/house-rules
claude plugin install house-rules@house-rules --scope user

Set up one project. The project folder must be a repository, a folder Git tracks, because setup reads the project's default branch and the checker only looks at files Git tracks. If yours isn't one yet, ask Claude Code to make it a repository and put it on GitHub. Then open a terminal in the project folder, start Claude Code by typing claude, and run:

/house-rules:bootstrap

It looks over the project and proposes a house.json listing the modules that fit. Once you approve, it writes the rule files, the checker, the lock file and a short index of the rules into your copy. It also gives you a starter block for your instruction file, which you paste in yourself.

Check any time. From the top folder of the project:

node .house/check.mjs

It prints any findings and warnings, then a one-line summary; a clean run reports zero findings. It's also worth adding to CI, the service that runs a project's checks on every proposed change.

What to expect afterward

Updates arrive as a plan you approve. When the package changes, or when you change house.json, run /house-rules:sync inside the project. It shows what it would change and waits for you. Take what you want and decline the rest. If you've edited one of the package's files by hand, the update won't overwrite your edit: it stops and shows you the difference.

When the checker reports something, you have three options.

  1. Fix what it found: a renamed script, a document pointing at a moved file, a file that's grown too long. Most findings end here.
  2. Record that you're doing it differently. Add a deviation to house.json: a dated note of what you declined and why. The checker reads it on every run, so the exception is documented instead of forgotten.
  3. Change the package. If a rule file itself needs editing, propose the edit to the package rather than changing your copy, then run /house-rules:sync to pull in the new version once you approve it. Until then, sync leaves your hand-edited file alone.

Where to ask. The project lives at https://github.com/dubbl-a/house-rules. Its issues page has forms for reporting something broken, proposing a rule change, or asking a question; the question form points to the Discussions tab. The rules keep changing, and disagreeing with one is a good reason to open an issue.

Glossary

  • Repository (repo). Your project's folder of files, plus the record of every change to it.
  • Checkout. Your own copy of a repository, the one on your machine.
  • Commit. One saved snapshot of a change, with a message saying what it was for.
  • Pull request. A proposal to fold a separate line of work into the main one, opened so it can be reviewed first.
  • Module. A themed set of rules on one subject, such as docs or testing, turned on or off as a group in house.json.
  • Plugin. An add-on giving Claude Code extra skills and hooks.
  • Skill. A set of instructions Claude Code follows when you type its name after a slash, such as /house-rules:sync.
  • Branch. A separate line of work in a repository, made so a change can be worked on and reviewed apart from the main line.
  • Marketplace. A published list of plugins and where to get them.
  • Hook. A small program Claude Code runs just before an action, able to stop that action. The branch guard is one.
  • Lock file. A record of how each managed file looked when it arrived.
  • Fingerprint (hash). A short code calculated from a file's contents, which changes if the file does.
  • Checker. The command node .house/check.mjs, which rereads your project's documents and the files the package manages and reports where they and the project have stopped matching.
  • CI. A service that runs a project's checks on every proposed change, so a break is caught without anyone remembering to look.
  • Eval. A test of behavior rather than code: a real task, plus a check of whether the rules held. The cases come in pairs, one where the rule should hold and one where it should not fire.
  • Deviation. A dated note that this project declines a default, and why.
  • Ratchet. A line ceiling that tightens when a file gets shorter, so a trimmed file cannot grow back.
  • Anchor. The line under a rule naming what enforces it, or saying that nothing does.
