# Further token-cost levers for adopters (2026-11-08)

Research note. No rule, hook, agent, setting or plugin file changes with this note. It follows `2026-10-20.md` and the triage on issue #326, and does not repeat what they cover.

## Short answer

The search found no new lever with a measured, material saving on Claude Code 2.1.319 with the 5.5 models. No changelog feature after v2.1.305 survived verification.

After checking the candidates against this repo, the picture is narrower than the run's own ranking:

- **Nothing here justifies a build yet.** The one number at grade A is the Batch API's 50% discount, which does not apply to Claude Code runs.
- **The run's top candidate is mostly native already.** Claude Code staggers workflow fan-outs itself. Only parallel launches through the Agent tool remain, and their size is unknown.
- **The next useful step is measurement, not a feature:** three cuts of the existing transcript data, listed under "What to do next".
- **Two popular ideas should not ship on this evidence:** LSP-first rules, and cutting always-on text without a blind comparison.
- **The largest band has no fix here.** Main turns over 200k context were 84.5% of main cost, and nothing that survived verification measures a structural way to shrink them.

A thin result is a real result: the cheap levers with evidence were taken in October.

## How this was researched

One deep-research run with the tiered fork at deep depth and every claim verified: 5 angles, 296 agents, about 14.7M subagent tokens, 25 sources fetched, 88 claims extracted, 88 verified by three votes each. 82 were confirmed and 6 refuted, leaving 13 findings after synthesis. 3 search results were cut by the fetch limit. 65 of the kept claims carry a weak-source label: faithfully quoted, but opinion, vendor or forum material.

The question excluded everything already shipped, everything rejected on #326, and known native features. The session then checked the surviving candidates against this repo, including the harness survey. Those checks are marked "Repo check" below; the run itself did not see them.

Evidence grades: A primary docs or list price; B controlled but preliminary study; C single practitioner measurement; D assumption-based or none.

Each lever is flagged WORK-UNCHANGED (cannot change what an agent knows, reads or outputs) or NEEDS-A/B (can change it, so it ships only after a blind same-input comparison across many real tasks, per the rule that quality outranks small or moderate savings).

## Levers

### Batch API (metered only)

The Message Batches API halves the price of all usage, and caching multipliers stack on it: Sonnet 5.5 at $1/$5 against $2/$10, Opus 5.5 at $2/$10 (https://platform.claude.com/docs/en/build-with-claude/batch-processing, https://platform.claude.com/docs/en/about-claude/pricing). Confidence high, 3-0.

- **It does not apply to Claude Code.** Interactive and headless runs have no batch mode, so a plugin should not present CI, routine or `-p` runs as discounted. Capturing it means the plugin calls the Messages API itself. Agent loops cannot use it, because each step waits on a polled result.
- **Limits:** 24-hour window with most batches under an hour, no streaming or fast mode, 100k requests or 256 MB, 29-day result retention, not eligible for zero data retention.
- **Cache hits inside a batch are best-effort, 30% to 98%.** In one blog's recomputed Sonnet 5.5 example of 10,000 requests, cached standard calls cost $44.00, and batch cost $47.20 at 30% hits and $22.72 at 98%. Batch beat cached standard only above about 39% hits (https://blog.laozhang.ai/en/posts/claude-batch-api). Secondary and arithmetic.
- **Size:** 50% of whatever spend moves. The movable share is unknown and probably small, since the adopter profile is dominated by interactive agent loops.
- WORK-UNCHANGED when the same prompt already runs as one call. Rewriting a loop into one prompt is NEEDS-A/B: compare review findings from the loop and the single prompt, blind, across real PRs.

### Staggering subagent launches

Each non-fork subagent pays its own cache write, so simultaneous launches multiply the fixed floor, while a later launch of the same type can read a prefix an earlier one wrote (https://dev.to/nomurasan/i-measured-claude-codes-prompt-cache-cost-three-ways-85-of-it-wasnt-mine-to-trim-48hm). One practitioner measurement, on v2.1.126 with Sonnet 4.6. The upper bound is (N-1)/N of the shared floor.

**Repo check: workflows already do this.** `docs/handbook/sources/harness-survey.md:447` records, from https://code.claude.com/docs/en/workflows, that Claude Code holds all but the first agent in a fan-out sharing model, effort, agent type, tools, output schema and working directory until the first response begins (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, default 5000 ms). The run did not surface this. So the lever survives only for parallel launches through the Agent tool, such as several builders or researchers in one message, and the documentation found does not say whether those are staggered. That first needs a check of the transcripts.

The adopter's largest subagent cost, workflow agents at $212 of $517 in October, is therefore already covered natively if that session's Claude Code had the feature.

### Fork versus roster agent by parent context size

Forks reuse the parent's cached prefix and are already the default (interactive from v2.1.232, everywhere local from v2.1.302, per third-party posts https://finisky.github.io/en/claude-code-fork-cache/ and https://claudcod.com/blog/claude-code-fork-subagents/). A different model, tool set or system prompt cannot reuse the full prefix. What a plugin could add is a choice of when to use one, because a fork is cheap to start and expensive to continue in a large session.

Arithmetic, not a measurement, recomputed by the session at the 0.05x read rate for the 5.5 models (see Corrections): against a fresh 58k subagent on a 5-minute write, a fork of a 200k parent on the same model loses after about 10 turns. Against a Sonnet roster agent, a fork of a 200k Opus parent loses after about 4. It ignores output and per-turn tail writes. Near a 71k parent, the fork wins for almost any task length on the same model.

NEEDS-A/B, because a fork knows the whole conversation and a roster agent does not: run the same delegated tasks both ways, judged blind.

### Prefix stability of plugin-injected text

The mechanism is real: a change invalidates its cache level and everything after it. Timestamps, reordering and early edits are breakers. Other harnesses show design precedents (https://codex.danielvaughan.com/2026/04/21/codex-cli-prompt-caching-maximise-cache-hits-cost-reduction/, https://yage.ai/share/grok-bot-context-engineering-en-20260827.html). No source measures a saving.

**Repo check:** a search of `plugins/house/hooks/session-start.mjs` shows clock values only in lock handling and a state file. The orchestration text goes into `additionalContext` as it is read from the file. So there is no sign of a house-caused break for a checker to catch. A checker would guard against future regressions only, and the cost report already attributes rebuild causes. This was a search of that one hook, not a byte comparison across sessions.

### Subagent cache lifetime

`subagentPromptCacheTtl` exists (v2.1.242+) and Anthropic documents it for agent teams (`docs/handbook/sources/harness-survey.md:431`). No evidence shows that tuning it saves money. Raising subagents to 1h pays only if roughly two of every three writes get a reuse arriving after 5 minutes (derived: 1h adds 0.75x per write, each avoided 5-minute rewrite saves about 1.15x to 1.2x). A verifier saw a GitHub issue title suggesting the setting does not reach built-in or workflow subagents, but did not read the issue. Grade D, may be zero.

### Always-on text

Studies point in opposite directions, and cost seems to follow the behaviour files trigger more than their bytes.

- Lulla et al., 10 repos and 124 PRs: AGENTS.md associated with 28.64% lower median runtime and 16.58% lower output tokens, no input or cache tokens reported (https://arxiv.org/abs/2601.20404).
- Gloaguen et al.: context files raised inference cost by over 20%; generated files lowered correctness in 5 of 8 settings; human-written ones gained about 4%, inconsistently (https://arxiv.org/abs/2602.11988). Read through abstracts and secondary summaries, not the full paper.

The candidate is a deletion criterion, "delete anything the agent can discover by reading the code", which differs from the shipped length checks. That filter is practitioner opinion. NEEDS-A/B: current rules against pruned rules on the same real tasks, blind review of outcomes.

The startup ceiling is also low. In one old measurement, user layers were about 15% of cache creation and 85 skills added about 3k tokens (v2.1.126). The adopter's 71k median against that measurement's 46k is an unexplained gap worth breaking down before any trimming.

### LSP: do not ship as a cost rule

Measured from about 14% cheaper to 118% more tokens.

- A preliminary five-arm ablation found LSP raised tokens 6% to 118% on symbol localization with no recall gain, and saved tokens only for the weakest model. Location-only LSP missed call sites in about three-quarters of multi-file renames that grep solved (https://arxiv.org/abs/2608.13568, via https://buttondown.com/patricknovak1/archive/models-agents-ep144-language-server-retrieval-costs-more-tok/).
- CircleCI's vendor post, 3 tasks on vuejs/core: 3% cheaper on Opus, 14% on Sonnet (https://circleci.com/blog/claude-code-lsp/).
- All models tested predate Claude 5.5.

If pursued at all, NEEDS-A/B: a router sending reference-heavy work to LSP and the rest to grep, compared blind on real localization, reference and rename tasks.

### No surviving evidence

Repo maps and indexes, refuter and review rework, and handoff or checkpoint designs that shrink post-compaction context produced no surviving claims. That is an absence of evidence, not evidence of no value. Any design for the over-200k band would change what the agent knows, so it would be NEEDS-A/B.

## What to do next

Each of these is a cut of transcripts `plugins/house/scripts/cost-report.mjs` already reads. Each changes nothing about the work.

1. Of the $321 short-TTL subagent writes, how much came from same-type Agent-tool launches in one message whose first request read no cache? This decides lever 1.
2. How much delegated spend is automatic forks from parents over 200k, and do they run past the break-even turns above? This decides whether fork versus roster is worth an A/B.
3. What makes up the first-request median of 71k main and 58k subagent on 2.1.319? This decides whether any startup trimming is worth an A/B.

Separately, whether any adopter has single-shot, step-independent model calls to move to the Batch API, and could accept the lack of zero data retention.

## Corrections made after the run

- **Read rate.** The run left 0.05x against 0.1x open and gave the fork break-even as "4 to 9 turns" and "1 to 3". The handbook records 5% cache reads on Opus 5.5 and Sonnet 5.5 (`docs/handbook/claude-code.md:656`), so this note uses 0.05x and about 10 and 4 turns.
- **`subagentPromptCacheTtl`.** The run found no Anthropic doc for it. The harness survey quotes one on agent teams.
- **Staggering.** The run ranked it first on seat plans without knowing workflows do it natively.

## Refuted claims, which this note does not rely on

- LSP cut tool-output tokens by about 31% to 33% on symbol call-site search (0-3).
- A cache TTL precedence order that lets a plugin control subagent write cost through a settings key (0-3).
- OpenAI cached input at 50% with no write fee, making one article's figures inconsistent (1-2).
- Developer-written context files lowered SWE-bench Lite success to 29.6% against 33.5% on GPT-4o (0-3).
- Sonnet 5.5 cache multipliers of 1.25x, 2x and 0.1x with reads at $0.10 and 5-minute writes at $2.50 per Mtok (0-3).
- Context files help only where a repo lacks its own documentation (1-2).

## Caveats

- Nothing here measures cache-write volume or savings on Claude Code 2.1.319 or the 5.5 models. The only first-hand Claude Code cache measurement is one project on v2.1.126 with Sonnet 4.6.
- Most fork, TTL and prefix-stability material is third-party blog analysis, some of it reverse-engineered.
- The adopter profile is one repo over three months; dollar figures are list-price estimates from October.
- The ETH Zurich study's context files were smaller than this adopter's whole first-request context, and the two are different quantities.
- The session's repo checks were searches of named files and the harness survey. The native staggering entry is from the survey's reading of the docs and was not re-fetched today.
